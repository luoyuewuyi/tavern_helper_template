## 先分清错误层

“某个名字的角色无法导入”不能直接归因于方括号、空格或中文。逐层确认：

1. 酒馆 API 能否按原名 `getCharacter(name)` 读取；
2. 头像 URL 是否对路径段做了百分号编码；
3. 本地目录与 `tavern_sync.yaml` 使用的是显示名、别名还是路径；
4. YAML 中含 `[]:#` 等字符的标量是否正确引用；
5. 失败发生在角色读取、头像下载、世界书读取、Schema 解析、文件写入还是 bundle；
6. 错误消息中的名称究竟是角色名还是被错误推导出的世界书名。

只有对应层的证据才能决定修复。不要通过删方括号、替换空格或改角色显示名来绕过同步器逻辑错误。

## 自动 push 默认

本技能所有者已经明确长期授权：凡是本次任务实际新建或修改了角色卡，且当前项目使用 TavernSync，AI 在本地验证通过后必须主动执行最终 TavernSync push，不需要再次询问，也不能把 push 留给用户。若 `tavern_sync.yaml` 尚无本次角色条目，按相邻角色卡配置的格式补入显示名、本地索引和导出路径后继续。

执行边界：

- 自动授权仅覆盖本地 SillyTavern 中本次目标角色卡；不包含 Git push、CDN、公开发布、删除或无关角色写入。
- 只读审查、解释、诊断或报告没有角色卡改动，不执行 push。
- 先用配置的键名作为 CLI `<配置名>`，以 `酒馆中的名称` 作为目标角色名；不要把两者混用。
- 目标条目缺失时先新增配置；只有项目根本没有 TavernSync 工具链，才把“无法自动 push”作为环境限制报告。
- 正常更新先运行不带 `-f` 的 push；仅在创建新角色、已确认条目差异需要覆盖或项目规则明确要求时使用 `-f`。
- push 必须发生在所有源码、构建、bundle 和引用更新完成之后。push 后若再改任何内容，旧 push 立即失效，必须重新执行。
- push 失败或回读不一致时，任务仍在进行中；继续修复、重新验证和 push，不得以“请用户自己 push”收尾。

流程顺序固定为：

```text
实现 → 本地检查／构建 → bundle 解码 → 最终 push → 隔离 pull／API 回读 → 报告
```

其中 push 是最后一次写操作，回读是只读验收。

## push 成功不是保存成功

截至 2026-07-11 核验的 StageDog/tavern_sync `main`：

- 服务端 `push_once()` 等待 `emitWithAck('push_character', ...)`，但不检查 ACK 返回内容，随后直接打印“成功推送”；
- 浏览器端 `push_character` 监听器启动异步角色写入后没有 `await`，立即调用 ACK；异步写入若稍后失败，终端仍已得到成功结果；
- 客户端先创建／替换世界书，再更新角色。因此可能出现“世界书已经增加，角色描述与第一条消息仍是旧值”的部分成功。

这不是推测性的措辞问题，而是传输确认和持久化确认被混在了一起。TavernSync stdout 只能称为“push 请求已被浏览器脚本接收”，不能单独证明角色已保存。浏览器 toast 和控制台中的“已推送角色卡”比终端 ACK 更靠后，但最终仍以 `getCharacter` 或隔离 pull 回读为准。

若上游更新，先重读当前 `src/server/syncer/interface.ts` 和 `dist/script.js`；只有 ACK 真正等待角色更新、错误会回传且回读一致时，才可降低这条防护。

## 角色 push 的头像前置条件

当前浏览器脚本在角色 push 中无条件执行等价于：

```ts
character.avatar = new Blob([new Uint8Array(character.avatar)]);
```

因此本地角色配置使用 `头像: ""`、`avatar: ""`、`null` 或省略头像时，传输对象会得到 0 字节头像。不同酒馆／助手版本可能在创建或更新角色时以不同方式失败，但由于 ACK 提前返回，常见外观是：世界书成功、角色本体没有更新、终端仍报告成功。

实时 push 前强制检查：

1. `头像`／`avatar` 是非空文件引用；
2. 省略扩展名后只能命中一个文件；
3. 文件不是 0 字节，魔数确实是 PNG、JPEG、GIF 或 WebP；
4. 打包后的容器按魔数识别，不能因为后缀叫 `.png` 就认定它是 PNG；
5. 无头像卡只走目标工具明确支持的 JSON／CHARX 打包或导入流程，不直接套用当前 TavernSync 角色 push。

新角色没有可用头像来源时，正确流程是停在 TavernSync push 之前并说明“正文／世界书／本地包已完成，缺少合法非空头像，尚未发送 push”。只可使用用户提供的图片、项目中明确属于该角色的现有素材，或用户明确授权后生成的图片；不得从别的卡复制头像、擅自下载版权不明图片或临时生成占位图来绕过检查。

可先运行：

```text
node <skill>/scripts/check_character_roundtrip.mjs <项目目录> --tavern-sync
```

没有提供产物或回读时，这个命令会故意返回 WARN；它只完成前置检查，不会假装已经导入。完成 bundle 后再加 `--artifact <产物> --strict` 进入下一道门。

## 隔离回读闭环

执行角色 push 时，按以下固定顺序；本技能所有者的自动授权见上节：

1. 对源项目运行 `check_first_message_refs.mjs --strict`；
2. 运行 bundle，按魔数重新解析最终 PNG／JSON／CHARX；
3. 用 `check_character_roundtrip.mjs --artifact <产物> --tavern-sync --strict` 比较主开场和所有备选开场；
4. 执行 push；此时只记录“push 已发送”；
5. 在 `tavern_sync.yaml` 添加一个临时验证配置：使用相同 `酒馆中的名称`，但把 `本地文件路径` 指向全新的隔离目录；
6. 对验证配置执行 pull，禁止首次回读覆盖正式项目；
7. 运行 `check_character_roundtrip.mjs <源项目> --readback <隔离目录> --tavern-sync --strict`；
8. 若隔离 pull 保留了中文 `index.yaml` 与独立 MVU 文件，对隔离目录重跑 `check_status_variable_bridge.mjs --variables-only`；若同步器只回读打包字段，则人工／脚本核对四条协议的等价启用状态、initvar 关闭状态和关键 `stat_data`，并注明回读形态；
9. 只有回读的开场数量、逐项 SHA-256、非空头像和适用的 MVU 协议都一致，才能报告“已导入并回读”；
10. 删除临时配置和隔离目录；保留验证输出摘要，不把临时副本混入交付物。

检查器输出的 `verifiedLevel` 和 `allowedClaim` 是措辞上限：`artifact` 即使 PASS 也只允许报告“已打包并解码”，必须达到 `target-readback` 才允许报告“已导入并回读”。

临时配置示例：

```yaml
配置:
  __开场回读验证:
    类型: 角色卡
    酒馆中的名称: 保守世界
    本地文件路径: .verify/保守世界/index
    导出文件路径: .verify/保守世界/artifact
```

角色定义回读成功后，仍要区分聊天历史：SillyTavern 的第一条消息是在开始新聊天时作为初始 greeting 使用。已有聊天的首楼是已保存消息，不会因角色字段更新自动等同于新值。界面验收应新建聊天或经明确授权重置／替换首楼，再检查可见内容；不要继续让用户“刷新试试”。

## 名称与路径规则

- 调用 API 时保留角色原始显示名；URL 路径段使用 `encodeURIComponent(name)`／等价编码，不手写把空格替成 `%20` 后又二次编码。
- 本地目录名可以使用安全别名，但同步配置中要明确把别名映射到真实角色名；不要在不同文件暗含不同清洗规则。
- PowerShell／shell 文件操作使用字面路径参数，避免 `[]` 被当通配符。
- YAML 对含方括号、冒号、井号、前导特殊字符的名称使用引号。
- 诊断日志同时记录原始角色名、编码后的请求路径和目标绝对路径，方便定位是哪一层改变了名称。

例如 `Haanja [Sinisistar 2]` 的头像路径应是：

```text
/characters/Haanja%20%5BSinisistar%202%5D.png
```

这只能证明 URL 编码正确；后续世界书逻辑仍可能失败。

## 世界书三态语义

角色配置必须区分三种状态：

| 本地值 | 语义 | 拉取／推送要求 |
| --- | --- | --- |
| 字段省略，或模板约定的 `与角色卡名称相同` | 使用同名世界书 | 同步器可把它解析成角色名 |
| `null` | 明确不绑定世界书 | 保持 `null`，条目为空；不得创造或查找同名世界书 |
| 非空字符串 | 绑定指定世界书 | 严格读取／写入该名称 |

空字符串或只有空白的字符串不属于第四种状态，必须在 Schema 层报错。`undefined` 与 `null` 不等价，代码不能用 `if (!worldbook)` 或 `worldbook ??= characterName` 合并它们。

`worldbook: null` 与非空 `entries` 是矛盾数据，必须拒绝 pull／push 并说明会丢失哪些条目；不得用“不创建世界书”静默忽略条目。推送合法的 `null + []` 时应解除角色绑定，但不要擅自删除之前存在的世界书文件；删除是另一项有破坏性的操作。

## 已确认的无世界书故障

在 TavernSync 上游提交 `2f67d4b6fd4d5d796a38ad36eae3ce9e177530c9` 的客户端中，拉取逻辑曾将：

```ts
character.worldbook ?? data.name
```

用于世界书名称。角色 API 明确返回 `worldbook: null` 时，`null` 被重写为角色名，随后同步器尝试读取并不存在的同名世界书。于是错误看起来像“含特殊字符的角色名无法导入”，根因却是无绑定世界书状态丢失。

只删除这一行还不够：服务端传输 Schema 原本要求 `worldbook` 必须是字符串，保留 `null` 后会在下一层解析失败。完整修复必须同时覆盖：

- Tavern 侧 Character Schema 允许 `string | null`；
- pull 保留 `null` 且不调用 `getWorldbook`；
- push 只把 `undefined`／同名占位符解析为角色名，保留 `null`；
- push 收到 `null` 时解除绑定，不创建或改写世界书；
- 空字符串以及 `null + 非空 entries` 明确报错，不静默猜测；
- 中英文 Schema 描述明确三态语义。

本技能附带针对该基线的参考补丁：[`../assets/tavern-sync/no-worldbook.patch`](../assets/tavern-sync/no-worldbook.patch)。补丁不是永久替代上游升级；应用前必须核对提交和实际 diff，上游修复后优先使用上游实现。

## 安全复现与修复

1. 保存工作区已有修改和同步器版本／提交；
2. 选取一个能由 `getCharacter` 成功读取、但返回 `worldbook: null` 的角色；
3. 在隔离端口和临时输出目录执行 pull，避免覆盖已有卡；
4. 记录角色 JSON、头像下载、报错阶段和生成文件；
5. 在干净的同提交源树应用补丁并构建；
6. 重跑隔离 pull，确认输出保留 `世界书名称: null` 与空条目；
7. 将缺失文件定点复制进正式项目，不覆盖用户已有的角色描述、首条消息或手工条目；
8. 执行项目自己的 bundle／导入解析测试；
9. 如修改了酒馆内全局 TavernSync 脚本，记录本地补丁元数据，升级上游时先检查修复是否已合并。

不要在正式项目直接做首次 pull 测试；pull 可能按同步器策略重写索引或文本换行。

## 开场故障矩阵

| 证据 | 结论与下一步 |
| --- | --- |
| 源项目开场为空／引用失效 | 先修 `index.yaml` 与文件引用，禁止 bundle 或 push |
| 源项目非空，产物 `first_mes` 为空 | 打包映射或引用解析失败；检查产物本身，不碰聊天缓存 |
| 产物正确，push stdout 成功，隔离 pull 仍为空 | 目标角色写入失败；查头像、浏览器控制台、助手版本和角色更新 API |
| 世界书已更新，角色字段仍旧 | 符合客户端“先世界书、后角色”的部分成功；优先检查角色更新阶段，不重写世界书内容 |
| 隔离 pull 与源项目同哈希，当前聊天仍无开场 | 角色定义已正确；当前聊天首楼是旧历史。新建聊天或显式重置首楼验证 |
| 新建聊天仍为空，但 API 回读非空 | 检查所选角色／群聊、当前 chat、首楼正则和显示层；不要再次改 `first_mes` 猜格式 |
| `.png` 后缀但魔数是 JSON | 产物命名或打包容器选择错误；按实际容器修正，禁止把后缀当解析证据 |

## 回归矩阵

至少覆盖：

| 名称／世界书 | 预期 |
| --- | --- |
| 普通 ASCII 名 + 同名世界书 | 正常 pull/push |
| 空格、方括号名 + `null` | 保留原名和 `null`，不查询同名书 |
| 中文／非 ASCII 名 + 指定世界书 | URL、路径、YAML 均不乱码 |
| 特殊名 + 字段省略 | 按项目约定解析同名书 |
| 任意名称 + 空字符串世界书 | Schema 明确拒绝 |
| 任意名称 + `null` + 非空条目 | 明确拒绝并提示矛盾，绝不静默丢条目 |
| 特殊名 + 不存在的指定书 | 报告准确的世界书名，不误报角色名 |
| 已有本地手工文件 | pull 验证不应无提示覆盖 |
| `null` 推送到此前绑定过书的角色 | 解除绑定，不删除旧书 |
| bundle 后 PNG／JSON 再解析 | 名称、首条消息、扩展字段和 `null` 保持 |
| 非空头像 + 非空主开场 | push 后隔离 pull 与源文件逐项同哈希 |
| 空字符串／null／省略头像 | TavernSync 前置检查明确拒绝，不发送可能假成功的 push |
| push 后继续查看已有聊天 | 不把旧首楼误报为角色字段未保存；另建新聊天验收 |
| 浏览器端异步角色更新失败 | 终端 ACK 不得作为成功，隔离 pull 必须揭示差异 |

最后分别报告“源项目通过”“bundle 解码通过”“push 已发送”“目标角色回读通过”“新聊天首楼通过”。前一层成功不能替后一层背书。
