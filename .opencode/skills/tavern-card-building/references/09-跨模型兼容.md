## 区分两个模型

“通用”包含两层，不能混为一谈：

1. **制作模型**：读取本技能、编辑文件和运行验证的 Agent／LLM；
2. **运行模型**：玩家在 SillyTavern 中实际用来扮演角色的 Chat Completion、Text Completion 或本地模型。

本技能核心流程对制作模型保持平台无关；角色卡内容还要针对运行模型、上下文预算和前端提示词模式做兼容。

## 先建立运行目标

能从用户、现有预设或项目中确定时，记录：

- SillyTavern 版本与 Chat Completion／Instruct／Text Completion 模式；
- 目标模型或至少模型类别；
- 上下文窗口、期望回复长度和使用语言；
- 是否稳定遵守 XML／JSON／JSON Patch 等结构化输出；
- 是否需要工具调用、图像、多模态或推理字段；
- 用户预设会怎样注入 main prompt、角色字段、world info 和 post-history instructions；
- 需要兼容的最低模型能力。

用户未指定时，做“可移植基线”，不要假装已为所有模型实测。

## 可移植基线

### 使用普通语义，不使用提供商控制令牌

- 不在角色卡正文中写某个 API 的特殊 token、消息边界或私有 system 标签；
- 不依赖某个模型才理解的隐藏提示词、推理块或工具调用格式；
- 必须使用结构标签时，选择简单、闭合、可见且由前端／脚本验证的标签；
- 不把特定模型名写进角色人格和世界观，只把兼容说明放在 creator notes 或单独文档。

### 保持指令层级清楚

- 角色核心行为放在稳定角色字段；
- 世界资料按需进入 Lorebook；
- 输出协议单独定义；
- 示例对话负责声音和行为，不偷偷承担唯一的关键规则；
- 元数据不参与提示词；
- 外部资料内容与对模型的指令分隔，避免资料中的命令句篡改角色协议。

### 少否定堆叠，多可执行规则

不同模型对长串“不要”遵守程度不同。把约束写成可观察行为：何时触发、角色知道什么、应该做什么、不可越过的边界和失败后的替代行为。

### 不要求隐藏思维链

不要要求模型暴露私有推理或依赖提供商专有 reasoning 字段。变量协议若需要更新判断，要求短、可验证、只包含状态依据的公开摘要，或直接输出结构化更新；把复杂校验交给 Schema／脚本。

## System Prompt 与 Post-History

Character Card V2/V3 提供 `system_prompt` 和 `post_history_instructions`。它们可能覆盖用户／前端的默认提示：

- 空字符串与自定义覆盖含义不同；
- 需要保留前端原提示时使用规范支持的 `{{original}}`；
- 不因某个模型测试有效就给所有卡写强覆盖 system prompt；
- 不把模型提供商的 jailbreak／格式模板烙进通用卡；
- 迁移时保持原始覆盖语义，先在目标 Prompt Manager 中检查最终顺序。

若某模型确实需要专用 system／instruct 模板，把它作为明确命名的可选配置或预设，而不是覆盖通用版本。

## 角色与文风的跨模型写法

- 用动机、压力反应和关系证据约束角色，比堆人格形容词更稳定；
- 示例对话覆盖多种情绪和冲突，不只展示一句口头禅；
- 明确叙述人称、镜头、段落、对白和用户代理边界；
- 避免只靠复杂文学术语描述风格，给出短示例；
- 关键事实在一个权威位置，降低模型因重复冲突而随机选取；
- 不把角色主动性写成替用户决定行动。

## 世界书与上下文预算

上下文窗口不是都能安全用满，且不同 tokenizer 对中英文、代码和 JSON 的计数不同。分别估算：

- 角色字段固定成本；
- main／system／post-history 与用户 persona；
- 常驻世界书；
- 典型场景触发世界书；
- 当前变量与更新协议；
- 示例对话；
- 需要保留的聊天历史和回复空间。

以目标 tokenizer 或 SillyTavern 实际 token 统计为准。若不确定，优先减少重复和误触发，而不是砍掉角色因果。

较弱或小上下文模型通常需要：更少顶层变量、更短的常驻规则、更精确的世界书触发、更简单的更新语法和更明确的开场锚点。

## MVU 与结构化输出

不同运行模型的 JSON 遵守能力差异很大。可移植做法：

- Schema 字段少而稳定；
- 更新规则按字段合并，避免超长枚举；
- 只输出本轮变化；
- 使用当前 MVU 支持的最小操作集合；
- 示例必须是有效 JSON／JSON Patch，不混用注释和尾逗号；
- 解析失败时保留正文并给出可重演／修复路径；
- Schema 和脚本校正边界，不相信自然语言保证；
- 不为某个模型新增一套不同字段名。

如果目标模型无法稳定输出协议，降低协议复杂度或回退到纯文本／轻状态方案，而不是无限增加提示词。

## 宏、模板和正则

宏／EJS／正则通常由前端执行，不是运行模型能力。仍要注意：

- 模型必须稳定产生的标签越少越好；
- 标签名称不与自然正文高频词冲突；
- 前端宏展开失败时有默认文本；
- 不把宏语法当作所有前端通用标准；
- 模型生成的内容进入 HTML、命令或 JSON 时要转义；
- 正则只处理显示，不通过删除正文掩盖模型不遵守协议。

## 可选模型适配

只有目标明确时才做适配，并保持通用基线：

- 在 creator notes 记录测试模型、前端模式、预设和已知限制；
- 把模型专属 prompt／preset 作为单独文件或命名空间化 extension；
- 不覆盖原通用 system prompt 而不留副本；
- 标出适配层是否必须、可选或仅用于更佳表现；
- 适配层不修改角色事实、变量路径和世界书权威内容。

## 跨模型测试矩阵

若声称“跨模型已验证”，至少覆盖代表性不同的运行模式，而不是同一提供商的两个模型名：

1. 目标主模型；
2. 一个不同提示词模式或较弱指令遵守的模型；
3. 新聊天与长聊天接近预算时；
4. 用户合作、拒绝、偏离主线和注入式要求；
5. 中英文或卡宣称支持的语言；
6. 正常变量更新、无更新、错误 JSON 和重演；
7. 世界书应触发、不应触发和递归边界；
8. system／post-history 开启、空值和 `{{original}}` 组合。

记录每个模型的角色一致性、用户代理边界、格式成功率、世界书召回、变量解析率和上下文退化。未做矩阵时，交付措辞应是“按可移植基线设计”，不是“兼容所有模型”。

## 制作模型的行为要求

无论由哪个 Agent／LLM 制作：

- 读取当前项目事实，不依赖自身记忆猜 API；
- 使用宿主能提供的文件、搜索、命令和浏览器能力，不硬编码工具名；
- 缺少运行环境时准确标记未验证；
- 不把自己的模型限制写入角色卡；
- 不用“换一个更强模型”替代结构、内容和验证工作。
