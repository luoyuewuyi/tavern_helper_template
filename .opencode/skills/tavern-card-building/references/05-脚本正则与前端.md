## 先选运行形态

| 需求 | 优先形态 |
| --- | --- |
| 隐藏／折叠协议块、替换占位符 | 正则 |
| 监听消息、操作变量、添加少量按钮 | 酒馆助手脚本 |
| 消息楼层内状态栏、阅读器、开场选择 | 前端界面 iframe |
| 酒馆原生页面上的常驻补充控件 | 脚本挂载父页面 DOM |
| 与酒馆样式隔离的常驻复杂控件 | 脚本创建独立 iframe |
| 跨楼层、多页面、复杂媒体或工作流 | 独立前端／插件 |

不要为了一个显示替换引入完整前端，也不要用复杂正则模拟应该由脚本维护的状态机。

## 正则

正则的合理职责：

- 把稳定占位符替换为状态栏或界面入口；
- 隐藏只供变量解析器使用的更新块；
- 折叠特定标签内容；
- 对用户输入和 AI 输出做明确、可测试的显示处理。

### 规则

- 明确来源：用户输入、AI 输出、斜杠命令或其他文本；
- 明确作用：只影响显示，还是也影响发给模型的文本；
- 匹配尽量使用稳定边界标签，不依赖易变自然语言；
- 避免灾难性回溯和吞掉相邻消息；
- 替换内容中的 `$1`、反斜杠、代码围栏和 YAML 引号要按当前序列化层验证；
- 若替换内容来自文件，先确认引用路径和最终导入产物；
- 不假定所有 UI 替换都必须 fenced HTML。复制当前项目成功正则的包装格式，并在目标版本实测。

为每条正则准备：最小匹配、典型匹配、跨行匹配、不应匹配、缺失闭合标签、含特殊字符六类样例。

## 酒馆助手脚本

### 使用高层 API

优先使用当前 `@types` 中的 Tavern Helper 高层函数；只有没有等价能力时才调用 Slash Command 或更底层 SillyTavern 内部对象。原因不是风格，而是高层函数有更稳定的类型、返回值和错误边界。

写代码前在 [`raw/api-types.txt`](raw/api-types.txt) 搜索函数名，确认：

- 参数作用域和默认值；
- 同步或 Promise 返回；
- 消息编号是否支持负索引／`latest`；
- 函数只可用于脚本、楼层 iframe 还是任意环境；
- 对应事件名称和监听器参数。

### 生命周期

- 初始化只执行一次，脚本重载时不重复挂监听；
- 为所有事件、定时器、Observer 和父页面 DOM 节点提供清理；
- `pagehide`、脚本卸载或项目提供的销毁钩子中清理；
- 异步任务处理取消、过期响应和错误提示；
- 事件处理器避免再次触发自己造成循环。

### 变量与消息

- 区分 global、character、chat、message、script、extension 等作用域；
- 历史消息、最新消息和当前楼层不是同一概念；
- 修改消息后按 API 要求刷新对应楼层，不靠直接改 DOM 持久化；
- 批量操作前读回目标范围，避免误删或旋转错误消息；
- 用户输入进入命令、HTML 或选择器前做对应转义。

## 楼层前端界面

模板项目通常把 `index.html` 保持为静态挂载壳，实际组件、脚本和 CSS 从 `index.ts` 导入并由项目打包器内联。沿用该方式；不要在已有模板上另建一套手写内联构建。正式状态栏、开局页、阅读器或楼层游戏界面必须采用多模块源码，详细边界见 [`10-多模块界面工程规范.md`](10-多模块界面工程规范.md)。单文件 HTML 只允许一次性诊断原型，不能作为正式交付。

典型入口流程：

1. 等待 DOM 和所需全局 API；
2. 等待目标消息的真实数据；
3. 创建 Vue／Pinia 或项目采用的应用；
4. 挂载到静态容器；
5. 安装或确认项目自带的 iframe 自动高度同步；
6. 在 iframe 销毁时解除外部监听、Observer 和定时器。

### 尺寸与响应式

酒馆助手当前参考实现会在消息 iframe 内观察 `body`，用 `body.scrollHeight` 更新 `frameElement.style.height`。不要假定所有目标版本、外部加载方式或嵌套 iframe 都会可靠保留这段运行时；正式界面应复用当前项目已验证的高度 helper，或在独立 `iframe-height.ts` 中提供同等逻辑。

高度同步至少覆盖：首次挂载、Vue `nextTick` 后、tab／折叠切换、异步列表或图片／字体加载后的尺寸变化。实现使用 `requestAnimationFrame` 合帧、`ResizeObserver` 观察 `body`、只在高度实际变化时写回，并在 `pagehide` 销毁。不要把 Observer 逻辑塞回 `index.ts` 或某个业务组件。

消息 iframe 的高度会受内容影响。避免：

- 用 `100vh`、大 `min-height` 或固定视口高度制造无限扩张；
- 内外层同时滚动；
- 绝对定位内容不参与文档流导致高度错误；
- 给 `html`、`body`、`#app` 设置 `height: 100%`／`min-height: 100%`，让测量值跟宿主高度互相反馈；
- 只按桌面宽度设计；
- 超长文本、长键名和本地化后溢出。

优先使用正常文档流、`height: auto`、容器宽度、必要的宽高比和明确的内部滚动区。若确实需要内部滚动区，给业务列表设有上限的 `max-height`，不要让根节点成为第二个全页滚动容器。测试内容展开后 iframe 是否增高、收起后是否回缩，以及窄屏、宽屏、字体放大和极端值。

### 数据原则

- UI 读取项目 store 或真实变量，不维护第二份持久化真相；
- 写操作通过变量／消息 API，成功后再更新显示；
- 加载中、无数据、错误和权限不足分别展示；
- mock 数据只用于开发预览，生产构建不能把它当回退；
- 对旧字段的兼容放在只读适配层，并记录移除条件。
- 明确区分只读字段和可写操作。只有装备、使用物品、确认选择等用户明确触发且协议允许的动作才直接写变量；状态栏不替用户决定目标、行动或剧情方向。

## 开局配置界面

开局界面用于收集玩家身份、背景、路线、初始地点或自定义开局，不等于剧情正文。先决定提交结果去哪里：从禁用的 `[initvar]` 产生的 0 层 `stat_data` 克隆出第 1 层快照、更新指定世界书／角色信息，还是作为首轮生成上下文。任何方案都不得启用或直接改写 `[initvar]` 条目。

- 玩家身份等长期信息与一次性开局描述分开存放；
- 写变量前按 Schema 校验字段、类型和层级；
- 没有变量结构时不要把任意表单数据硬写进 MVU；
- 默认保留自由填写入口，预设选项只作辅助；
- 提交应幂等，避免刷新或重复点击再次初始化；
- 明确开局界面是替代叙事开场、先于叙事开场，还是与开场共存；不要无意生成两次初始化或两段互相冲突的开场；
- 输入进入世界书、命令、HTML 或模型上下文前分别做校验和转义。

动态开局的标准完成路径是：校验表单 → 读取并深拷贝 0 层 `stat_data` → 按显式映射写入 Schema 路径 → 生成非空 `<maintext>` → `createChatMessages` 创建 assistant 消息并携带 `data.stat_data` → `getChatMessages` 回读断言。只有回读成功才能显示完成。可复制多模块骨架位于 [`../assets/dynamic-opening-vue/README.md`](../assets/dynamic-opening-vue/README.md)，完整契约见 [`12-MVU世界书与开局契约.md`](12-MVU世界书与开局契约.md)。

## 脚本中的界面

### 独立 iframe 控件

需要样式隔离或复杂组件时，优先使用项目提供的 `createScriptIdIframe`／等价助手创建与脚本绑定的 iframe。这样更容易管理生命周期和样式污染。

### 酒馆原生补充控件

需要紧贴原生按钮、消息或设置面板时，可由脚本挂载到父页面 DOM。此时：

- 选择器必须针对目标版本验证；
- 节点可能因聊天切换或页面重绘被替换；
- 样式通过项目的 teleport／style helper 隔离和清理；
- 不覆盖原生事件或全局 CSS；
- 重载脚本前移除旧节点。

## 流式楼层界面

只有在生成过程中必须实时渲染结构化内容时使用流式／伪流式界面。设计稳定分隔协议，处理半截标签、重复片段、重新生成和停止生成。渲染器必须能接受不完整输入，不应在每个 token 上重建整个应用。

## 独立前端或大前端卡

先定义它与酒馆的边界：

- 是消息楼层内容、常驻插件面板，还是独立网页；
- 谁负责生成、消息历史、角色切换和存档；
- 如何读取当前角色／聊天／变量；
- 失败时是否仍可回到普通对话；
- 是否需要多 API、多模型、媒体、摘要、分支或导入导出。

建议模块边界：

- 酒馆适配层：消息、变量、角色、事件、命令；
- 领域状态：卡的玩法和状态机；
- 生成服务：请求、流式、取消、重试；
- 持久化：版本化数据和迁移；
- UI：纯显示与用户操作；
- 构建／部署：产物、资源路径和版本。

不要让组件直接散落调用全局酒馆对象，否则版本迁移和测试会非常困难。

## 构建与资源

- 先读 `package.json` 和项目打包配置；
- 开发期已有 `watch`／同步监听时，不为每次小改重复完整构建；
- 最终交付执行项目要求的 build 和类型检查；
- 检查输出是否真正内联了目标脚本、样式和资源；
- 若构建产物需要回写正则或 `index.yaml`，检查最终索引而不只检查 `dist`。`iframe srcdoc` 等多层嵌入要按当前项目正确压缩与 HTML／YAML 转义，并重新解析或执行项目 bundle 校验；
- 相对路径在酒馆 iframe、CDN 和本地预览下含义不同，要分别验证；
- 自己部署的界面／脚本 URL 必须带稳定发布版本。优先不可变标签或提交：`repo@v1.4.2/...`；若持续从分支发布，则使用每次发布递增且整次会话稳定的查询参数：`index.html?v=1.4.2`；
- 禁止 `?t=${Date.now()}`、随机数或每次打开都改变的参数。它们会彻底绕过缓存，却不能证明用户加载了哪个版本，也无法复现问题；
- 发布步骤必须是一个闭环：更新版本号 → 正式构建 → 上传／推送产物 → 修改角色卡正则与脚本库中的真实 URL → 重新 bundle／导出角色卡 → 从该 URL 读回并核对版本标记。只改源码或只改部署目录都不算完成；
- 界面可在根节点设置 `data-ui-version="1.4.2"` 或向控制台输出一次版本，便于在酒馆中确认实际缓存命中；版本标记必须来自构建期常量，不在组件中手抄多份；
- `testingcf.jsdelivr.net` 视为开发／预览通道：可以沿用项目开发基线，但正式发布时要评估固定提交、标签或版本目录；
- CDN 失败应有可理解的错误或本地回退，不显示空白页；
- 发布新版本时同步更新实际引用点，不在多个文件留下不同 URL。

## 浏览器验证

能使用浏览器时，至少检查：

1. 首次加载无控制台错误；
2. 真实 `stat_data` 或消息内容正确显示；
3. 生成后无需手动刷新即可更新；
4. 按钮在成功、失败、重复点击时行为正确；
5. 重载、切换聊天、切换 swipe 后不残留旧监听或旧数据；
6. 窄屏、长文本、空列表和极端数值不破版；
7. 网络资源失败时有回退；
8. 显示正则没有把更新协议重新送进模型，或把正文误删。

视觉截图只能证明一帧。交互、事件、数据和控制台需要单独验证。
