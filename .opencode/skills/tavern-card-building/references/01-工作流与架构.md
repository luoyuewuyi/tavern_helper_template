## 目标

把“写一张卡”拆成可验证的内容工程、变量工程和界面工程，同时兼容模板项目、原始卡文件与历史自定义项目。先识别项目，再选择流程；不要反过来把所有项目强行改成同一种结构。

## 识别项目形态

### A. 模板源码项目

常见信号：

- 根目录有 `package.json`、锁文件、打包配置和同步配置；
- `src/<角色或项目>/index.yaml` 是角色卡索引；
- `世界书/`、`脚本/`、`界面/`、`第一条消息/` 分开维护；
- 类型来自项目 `@types`，构建产物进入 `dist`；
- 项目提供 `build`、`watch`、`lint`、`format` 或 `tavern_sync` 命令。

处理原则：沿用现有工具链。先读根目录规则、`package.json`、初始模板和公共 util，不自己发明第二套 Vite／webpack／内联器。MVU、世界书和开局规范直接使用本技能的硬契约与 `assets/`，不得翻找任意角色卡猜写法；任务本身若是迁移旧卡，该卡也是待审输入，不是规范基线。

### B. 原始角色卡或导出物

常见输入：PNG、JSON、YAML、世界书 JSON、聊天导出、正则 JSON。

处理原则：先保留原件并解析字段。确认角色卡规范版本、扩展字段和嵌入资源，再决定就地修补还是转为源码项目。PNG 不能只当图片看；角色卡元数据可能嵌在文本块中。

### C. 只有设定或需求

处理原则：先产出内容设计契约、开场和世界书计划。除非需求确实需要状态追踪或交互，不要预先搭 MVU 和前端。

### D. 历史自定义项目

常见信号：手写内联 HTML、外部 CDN、旧版全局 API、非标准目录、单个超大文件或特定卡专用构建脚本。

处理原则：先证明当前链路如何运行。修复时保持兼容；迁移应分阶段，并保留可比较的旧产物。不要把“模板现在这样写”直接等同于“旧卡必须立即重写”。

## 确认交付边界

在实现前写下本次真正需要交付的对象：

| 用户目标 | 默认交付 | 不自动包含 |
| --- | --- | --- |
| 写设定／开场 | 可审阅文本和对应源码 | MVU、UI、发布 |
| 新建完整角色卡 | 源码、开场、玩法所需的世界书／集成、构建验证；若有明确 TavernSync 配置，最终 push 与隔离回读 | 为形式增加 MVU／UI／无消费方的世界书，Git push、CDN／公开发布 |
| 修复现有卡 | 最小修复、回归验证、最终 TavernSync push 与回读、原因说明 | 顺手重构全部模块 |
| 做状态栏／楼层 UI | 数据契约、界面源码、接入与真实数据验证 | 独立站、插件化 |
| 迁移模板 | 可回退的迁移结果、差异与兼容验证 | 删除旧版本、强制发版 |
| 发布／CDN | 版本化产物与已授权的发布步骤 | 泄露密钥、覆盖未知远端 |

## 安全同步流程

1. 确认目标绝对路径和仓库根目录。
2. 查看工作区状态，区分用户已有修改与本次范围。
3. 本地项目存在时直接读取，不把 `pull` 当开场动作。
4. 只有以下情形才同步远端：
   - 用户明确要求拉取或更新；
   - 本地项目不存在，需要取得用户指定源码；
   - 项目规则明确要求，且已确认不会覆盖本地修改。
5. 构建可本地执行；本技能所有者已经长期授权本次目标角色卡的最终 TavernSync push，无需逐任务再确认。项目已有 TavernSync 但缺少本次角色条目时，按同文件格式补配置并继续；这不是等待用户的理由。Git push、发布、上传 CDN、删除或修改无关角色仍单独确认授权。
6. 绝不使用破坏性回滚清除用户改动来“解决冲突”。

## 架构选择

### 纯文本卡

适合角色扮演、关系推进和叙事体验主要靠提示词完成的任务。重点是角色行为因果、开场可行动性、世界书触发和示例对话。

### 正则／轻脚本卡

适合显示替换、折叠思维链或协议块、少量按钮和不需要持续结构化状态的增强。正则应负责显示，不负责修复错误数据。

### MVU 卡

适合数值、装备、任务、关系、时间、地点等需要随楼层持久变化的状态。新增 MVU 的前提是字段确实会变化且会影响玩法。

### 楼层 UI

适合在消息楼层内展示当前状态、阅读器、操作面板或开场选择。数据源仍应是酒馆／MVU 状态，不应复制成 UI 私有状态。

### 独立前端／插件

适合跨楼层常驻、复杂多页、媒体管理、独立存档、模型路由或深度控制酒馆原生界面的需求。成本最高，需要生命周期、权限、响应式、错误处理和发布策略。

## 分阶段实现

### 阶段 1：基线

- 项目能否解析、构建或导出；
- 现有首条消息和世界书是否被正确引用；
- 现有错误能否稳定复现；
- 当前目标版本和依赖版本。

### 阶段 2：内容骨架

- 角色核心冲突与关系动力；
- 开场场景和用户行动点；
- 世界书覆盖矩阵；
- 示例对话或风格锚点。

### 阶段 3：状态与协议

- 决定是否需要 MVU；
- 固定 Schema、初值和更新规则；
- 精确建立四条 MVU 世界书协议：`[initvar]变量初始化勿开` 显式关闭，另外三条运行时协议显式开启；四条均蓝灯且双向禁止递归；
- 明确模型输出、上下文注入和显示层之间的边界。
- 在接 UI 前运行 `check_status_variable_bridge.mjs <角色卡目录> --variables-only`；failure 不得带入下一阶段。

### 阶段 4：界面和脚本

- 先接真实数据，再做视觉；
- 正式界面按宿主 context、adapter、store、actions、高度生命周期、组件和样式拆成可维护模块；
- 动态开局必须创建并回读正文非空、携带 `data.stat_data` 的 assistant 消息，不能只修改前端状态或显示成功提示；
- 处理加载、空态、失败、重载和销毁；
- 避免只在演示数据上工作。

### 阶段 5：验证和交付

- 运行项目自带检查和构建；
- 检查真实环境中的关键路径；
- 在源码和最终导出中复核 `[initvar]` 仍明确关闭；新聊天实测 0 层初始化和开局消息回读；
- 对比修复前后或迁移前后产物；
- 确认 `tavern_sync.yaml` 的唯一目标配置；若项目使用 TavernSync 但目标条目缺失，补入角色名、本地索引和导出路径；
- 完成所有本地修改后主动执行最终 TavernSync push，不等待用户提醒；
- 用隔离 pull／API 回读目标角色并比较关键字段；
- 若回读后又修改任何源文件或产物，重新验证并再次 push；
- 报告最终 push、回读及其他已做与未做的外部动作。

“最终 push”指最后一次目标端写入；其后的隔离 pull 是只读验收。只读审查或诊断任务不触发 push，因为它们没有待交付的角色卡修改。

## 模板项目的常见事实

以项目本身为准，但当前主流 Tavern Helper 模板通常具有这些约定：

- 源码位于 `src`，脚本入口使用 TypeScript；
- Vue 3、Pinia、Zod 可直接按项目配置使用；
- 界面通常由 `index.ts` 导入组件和样式，再由打包器内联；
- `watch` 用于开发期热更新，`build` 用于最终产物；
- `tavern_sync` 负责项目与酒馆间同步；
- `index.yaml` 引用世界书、第一条消息、正则和编译后脚本。

不要据此硬编码命令。先读取 `package.json` 的 scripts 和同步配置；只运行项目实际提供的命令。

## 维护性

- 角色内容、变量结构、脚本、正则和界面职责分离。
- 大功能放入专门模块，避免继续膨胀单文件。
- Schema 是契约源；显示适配可以兼容旧字段，但不得悄悄修改持久化协议。
- 版本化外部资源，记录来源和构建方式，保证未来能重建。
- 删除旧实现前，确认新路径已接入且不存在双重输出或双重监听。
