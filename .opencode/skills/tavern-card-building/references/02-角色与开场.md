## 角色不是标签集合

可持续扮演依赖“原因 → 判断 → 行动 → 后果”，而不只是外貌、性格词和背景百科。每个核心角色至少回答：

- **想要什么**：短期目标、长期欲望、不能承认的渴望；
- **怕失去什么**：失败成本、禁区、羞耻或创伤；
- **相信什么**：价值观、偏见、对用户和世界的初始判断；
- **如何行动**：压力下的策略、习惯、语言和身体反应；
- **矛盾在哪里**：公开形象与私下需求、能力与弱点、爱与控制等冲突；
- **如何变化**：信任、关系、失败或真相会怎样改变其行为。

把抽象形容词改写成可演绎规则。例如，不写“高冷”，而写清：角色为何保持距离、用什么方式回避亲密、什么证据会让防御松动、松动后仍会保留哪些习惯。

## 关系动力

角色卡需要为 `{{user}}` 留出位置。明确：

- 双方如何认识，当前权力与信息是否对称；
- 角色对用户的初始判断，而不是替用户规定人格；
- 双方共同目标与冲突目标；
- 关系推进的证据和门槛；
- 可以恶化、误解、修复或转向的路径；
- 角色不可轻易越过的边界。

不要替用户决定未提供的外貌、身份、感受、台词或动作。若卡的玩法必须预设用户身份，把它写成明确可选前提，并提供替代入口。

## 可玩性检查

一个设定只有在能产生选择和后果时才算可玩。为每个重要设定补足：

1. 玩家如何遇到它；
2. 它改变了什么选择；
3. 谁会阻止、利用或误解它；
4. 成功、失败和拖延分别有什么结果；
5. 它如何与角色关系或世界状态联动。

至少准备几类可持续钩子：即时冲突、关系矛盾、长期谜团、世界事件、个人代价。它们不必全部常驻上下文，可由世界书按情境触发。

## 角色信息的分层

- **角色卡常驻字段**：身份、核心性格、关系前提、稳定的说话与行为原则。
- **世界书**：地点、组织、人物细节、机制、事件和按需知识。
- **示例对话**：声音、节奏、潜台词、不同压力下的表达。
- **变量**：真正会随剧情变化且会影响后续判断的状态。
- **仅显示信息**：排版、帮助、按钮提示等，不应污染模型上下文。

重复信息会浪费上下文并造成冲突。每个事实确定一个权威来源，其他位置只引用或压缩表达。

## 开场的职责

开场不是简介，也不是把设定一次讲完。它要同时建立：

- **角色锚点**：角色此刻的状态、欲望和独特行为；
- **场景锚点**：时间、地点、可感知细节和当前限制；
- **关系锚点**：角色如何看待用户，双方为何必须互动；
- **风格锚点**：叙述视角、节奏、对白密度和情绪；
- **剧情锚点**：已经发生了什么，接下来什么不能被忽略。

结尾停在冲突、选择、发现或情绪临界点，让用户有多种自然回应。不要在最后替用户做决定。

## 开场构建顺序

### 1. 选定时刻

选择“变化已经开始”的瞬间，而不是世界尚未发生任何事的静态早晨。常用入口：意外到访、交易条件、任务失败、关系重逢、秘密暴露、规则首次生效。

### 2. 先写动作和感官

用环境、动作、对话和具体物件呈现角色，不先用长段解释。必要背景只提供理解眼前选择所需的部分，其余交给后续剧情和世界书。

### 3. 给角色主动性

角色应正在做一件有目的的事，并对用户作出可识别的判断。避免角色只站着等待用户启动故事。

### 4. 留用户空间

给出清楚但不唯一的回应面：追问、拒绝、合作、观察、离开、欺骗或改变话题都能继续剧情。

### 5. 校准长度

长度由体验决定，不设统一字数。过短会缺锚点，过长会抢走用户第一步行动。删掉重复世界观和不能改变当前选择的信息。

## 多开场与动态开场

使用多个开场时，每个入口应带来真实差异，例如不同时间线、关系阶段、场景或玩法；不要只换背景句。

动态开场可由变量、宏、模板或脚本选择内容，但必须满足：

- 无脚本或宏失败时仍有可读的默认开场；
- 不把未转义的用户输入直接拼入 HTML 或命令；
- 随机结果可解释，必要时允许用户重选；
- 开场引用的角色、地点和变量在对应世界书／Schema 中存在。

## 开场落地与显示边界

开场内容写好后，还要依次通过四个不同对象；任一对象为空都不能用下一层的措辞汇报：

1. **源项目**：`index.yaml` 的第一项能解析到非空正文；备选开场的数量、顺序和文件引用明确。
2. **可导入产物**：重新打开最终 PNG／JSON／CHARX，主开场位于 `first_mes`，其余位于 `alternate_greetings`，内容哈希与源项目一致。
3. **目标角色定义**：同步或导入后，用 API 或隔离 pull 重新读取角色，确认目标端字段非空且同哈希。
4. **聊天消息历史**：在新建聊天或明确重置首楼后，首条可见消息才应来自新的角色开场。更新角色定义不会自动证明已有聊天里的旧首楼已被替换。

因此统一使用这些动词：

- “已写入”：只表示源文件已修改；
- “已打包并解码”：表示产物内字段已验证；
- “已发送 push”：只表示同步请求已发出；
- “已导入并回读”：表示目标角色定义已重新读取并一致；
- “新聊天已显示”：表示实际创建／重置聊天后检查过首楼。

TavernSync 的头像前置条件、push 假成功和隔离回读流程见 [`11-TavernSync同步与特殊名称.md`](11-TavernSync同步与特殊名称.md)。

## 文风设计

把“文风”写成可执行约束：

- 叙述人称与镜头距离；
- 句长、段落长度、对白与描写比例；
- 允许和避免的修辞；
- 角色的词汇、称呼、停顿和潜台词；
- 高压、亲密、冲突、日常四类场景下的差异；
- 不替用户行动、不总结式收尾等边界。

示例对话要展示变化，而不只是重复口头禅。至少覆盖日常、压力、拒绝、信任变化中的若干情境。

## 内容测试

完成后用不同用户策略模拟前几轮：

- 合作但追问细节；
- 拒绝角色提出的条件；
- 做出意外但合理的行动；
- 长时间不触发主线；
- 直接质疑角色的矛盾；
- 切换到安静日常场景。

检查角色是否仍遵守动机和边界、是否能主动推进、是否给用户选择、是否过早倾倒设定、是否在压力下变成无差别人格。

## 常见失败

- **标签堆叠**：有很多性格词，却没有触发条件和行为结果。
- **百科开场**：第一条消息解释完整世界，用户没有可做的事。
- **替用户写戏**：开场规定用户的心理、台词和决定。
- **全知角色**：角色知道世界书中不该知道的秘密。
- **瞬间关系跃迁**：好感或信任没有证据就跨越阶段。
- **只有主线**：用户偏离计划后角色失去行动能力。
- **设定与示例冲突**：角色卡说一套，示例对话训练另一套。

修复时优先补因果和行为规则，不靠继续添加形容词解决。
