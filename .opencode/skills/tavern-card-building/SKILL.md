# Tavern Card Building（通用版）

这是一套面向结果的角色卡工程流程。核心说明不绑定 Codex、Claude Code、Cursor、特定模型、特定子代理或特定浏览器工具；把宿主环境提供的读文件、搜索、编辑、命令行、浏览器和网络能力按需映射即可。

## 平台边界

本技能只用于 SillyTavern／酒馆。任务目标明确为 Tavo 时立即停止加载本技能，改用同级 `tavo-card-building/SKILL.md`；不得把 MVU、`[initvar]`、TavernHelper、Slash Command、酒馆正则字段或 iframe/CDN 界面套到 Tavo。任务只说“角色卡”而平台不明时，先用同级 `card-platform-router/SKILL.md` 确认平台。

## 执行契约

1. 先读取当前目录及父目录中的项目规则（如 `AGENTS.md`、`CLAUDE.md`、`.cursor/rules`、README）和现有实现，再动手。
2. 当前项目的规则、类型声明、公共工具和构建配置优先于本技能中的通用示例；不要为了“统一”而破坏能工作的项目约定。**不得把任意现成角色卡当 MVU、世界书、开局或界面的规范来源**；本技能的契约、绑定模板和目标环境类型已经足够。旧卡只可作为用户明确要求迁移／修复时的待审对象，不能因“它能导入”就复制其做法。
3. 保留用户已有修改。不得擅自覆盖、回滚、清空或重建不相关文件。
4. 本地已有项目默认直接检查和修改，不先拉取。仅在项目缺失、用户明确要求同步，或仓库流程明确要求且不会覆盖本地修改时拉取。
5. 构建、预览和本地验证属于正常实现步骤；Git push、发版、上传 CDN、公开发布、发送消息或其他远端写入仍须用户明确授权。**本技能所有者已明确长期授权一项例外**：对于当前任务实际新建或修改的角色卡，只要项目使用 TavernSync 且本地酒馆可连接，验证通过后必须主动执行最终 TavernSync push，无需每次再问；目标条目缺失时按项目格式补入 `tavern_sync.yaml`，不能以“尚未配置”为由停下。该授权只覆盖本地酒馆中本次目标角色卡，不覆盖 Git、CDN、删除或无关角色。
6. 不把密钥、令牌或私有端点写进角色卡、脚本、仓库、世界书或前端包。优先使用 SillyTavern 的密钥／连接配置。
7. 不以“文件存在”“页面能打开”代替完成。变量链、引用链、构建产物和实际交互都要按风险验证。
8. 严格区分“已写源文件”“已打包”“已发送 push”“目标端已保存”“新聊天已显示”。命令返回成功只能证明该命令实际确认的层级；未经目标端回读，不得称为“已导入”。

## 如何使用这部百科

本技能是完整知识库，不是要求所有角色卡机械执行同一套重型流水线。先按目标功能取用对应章节：

- **硬规则**只约束已经启用的功能和已确认会制造错误的事实。例如 MVU 卡的 `[initvar]变量初始化勿开` 必须显式关闭，不能把按钮提示写成“已导入”，TavernSync push 不能代替目标端回读。
- **适用流程**仅在项目确实包含该能力时执行。纯文本卡无需创建 MVU、前端或 CDN；静态开场卡无需实现动态开局事务；不使用 TavernSync 的项目无需执行 TavernSync 命令。
- **推荐验证**按复杂度和风险选择。复杂 Schema、跨版本操作符、移动端 UI 和远端资源需要更深验证；简单卡不应为了勾选清单平白增加模块。
- **可选增强**用于体验、维护性或兼容性，不是缺少即失败。若环境无法运行某项验证，准确标注“未实测”，同时完成其余可验证内容。

判断顺序始终是“这张卡有什么 → 对应知识是什么 → 哪些错误必须阻止 → 需要多少证据”，而不是先把所有章节套到每张卡上。

## 美化界面的默认原则

“是否使用 MVU”和“是否制作正式美化界面”是两条独立轴。只要用户要正式状态栏、开局页、楼层界面、阅读器或互动面板，默认采用多模块源码，不论数据来自纯文本、普通酒馆变量、宏、脚本计算还是 MVU。只有用户明确要求一次性极简片段／纯文字，或任务只是最小故障复现时，才允许单文件。

多模块和可维护性是实现手段，最终目标是界面真正更美观、更清晰、更有氛围且更好用。不得用“结构规范已通过”代替视觉质量：交付前必须检查主题一致性、信息层级、字体与间距、色彩与对比、图标、空态／错误态、交互反馈、动效节制、桌面与移动端效果，并通过真实截图或浏览器画面迭代。一个模块齐全但粗糙、拥挤、像默认表单的界面仍然不合格。

## 先判定任务形态

开始时确认以下四件事，并把不确定项通过现有文件和规则查清：

- **交付物**：角色卡内容、可导入卡包、源码项目、修复补丁、审查报告，还是发布产物。
- **项目形态**：模板源码项目、原始 JSON／PNG／YAML 卡、只有文本资料，还是历史自定义项目。
- **功能层级**：纯文本、世界书／正则、MVU 变量、楼层 UI、脚本插件、独立前端。
- **兼容目标**：目标 SillyTavern／酒馆助手版本、桌面和移动端、是否必须兼容旧卡。

若用户没有指定架构，选能满足体验的最低复杂度：

`纯文本 → 世界书/正则 → MVU → 楼层 UI → 独立前端或插件`

只有下一级无法稳定完成需求时才升级。前端不是角色卡质量的替代品。

## 资料优先级

遇到冲突时按以下顺序判断，并在交付说明中记录关键取舍：

1. 当前项目规则、锁定版本、类型声明和构建配置；
2. 目标运行环境实际导出的 `@types`、命令帮助和宏帮助；
3. 同项目受维护的公共工具、初始模板和模板仓库；
4. 官方或维护者当前文档；
5. 社区教程与历史卡经验。

社区教程用于学习设计思路，不用于覆盖已经变化的 API。任何模型记忆中的接口都不如当前类型声明可靠。

“项目规则优先”指遵守项目意图和工具链，不代表照抄已被当前类型签名或可复现实测否定的旧代码片段。发现规则示例与运行时声明冲突时，以目标环境的签名和复现结果修正规则，并记录冲突；不要为了服从旧文档继续制造已确认的 bug。

## 标准工作流

### 1. 盘点与建立基线

- 列出项目结构、入口、构建命令、同步配置、角色卡索引、世界书、脚本、正则和界面目录。
- 检查工作区是否已有修改，并把用户改动与本次范围分开。
- 使用项目的初始模板、公共 util 和本技能 `assets/` 建立骨架，不翻找其他角色卡来猜规范。若任务本身是修复／迁移旧卡，只读取该目标卡并把其现状视为待验证输入，不把它反向升级为规范。
- 对修复任务先复现或静态定位故障，记录预期行为与当前行为。

### 2. 写清设计契约

在编码前明确：

- 角色的欲望、阻力、矛盾、边界、关系动力和可持续剧情钩子；
- 开场必须建立的场景、关系、风格、冲突和用户可行动点；
- 如使用世界书：覆盖矩阵及每条职责；纯文本卡不为形式增加世界书；
- 如使用 MVU：Schema、初值、更新条件、显示字段和刷新事件，并写明四条协议世界书的精确配置；`[initvar]变量初始化勿开` 必须显式 `启用: false`，蓝灯仅表示它若被启用后的触发策略；
- 如使用 UI：数据源、空态、交互、移动端、失败回退和销毁清理；
- 如使用动态开局：表单字段到 Schema 路径的映射、非空 assistant 消息创建、`data.stat_data` 携带和创建后的回读断言；
- 哪些内容进入模型上下文，哪些只用于显示，哪些仅由脚本处理。

变量 Schema、初始化、更新规则和 UI 字段路径是一个耦合契约，应由同一实现上下文统一维护；不要拆成彼此不知道对方字段的独立工作。

### 3. 分层实现

- 先完成可玩的角色文本和开场，再按玩法需要补世界书。
- 若使用变量或格式协议，再建立稳定的变量／输出协议和正则。
- 若使用 UI、外部资源或独立前端，最后接入这些层。
- 模板项目沿用其 TypeScript、打包器、目录和同步方式；历史项目先保持兼容，再做有证据的迁移。
- 只做定点改动，避免用通用 YAML/JSON 序列化器重写整份人工维护文件，除非已确认不会改变格式、引用或扩展字段。

### 4. 验证闭环

按项目能力执行适用项：

- 结构解析、引用存在性、命名和路径检查；
- 类型检查、构建和项目自带测试；
- MVU 的 Schema → initvar → 更新规则 → `stat_data` → UI 完整链路；
- MVU 项目必须运行 `scripts/check_status_variable_bridge.mjs <角色卡目录> --variables-only`；initvar 被启用、缺少显式启用状态、运行时协议被关闭、初值为空或协议字段不完整均为未完成；
- 正则匹配样例、显示层与提示词层隔离；
- 在真实或本地可比环境中检查首屏、生成后刷新、按钮、重载、移动端和控制台；
- 打包后按文件魔数重开 PNG／JSON／CHARX，并比较主开场、备选开场和关键扩展；
- 导入／导出或同步流程的只读检查；有授权时才执行远端写入，写入后以隔离 pull／API 重新读取目标端，不以 push stdout 代替回读。

可按需运行 `scripts/` 中的审查脚本。它们是辅助证据，不得凌驾于当前项目协议；脚本给出警告后仍需阅读对应文件判断。

### 5. 最终 TavernSync push 与回读

对新建或修改角色卡的任务，验证通过后执行以下收尾；不得停在“文件已写好”或等待用户提醒：

1. 从 `tavern_sync.yaml` 确认唯一目标配置、酒馆显示名和本地索引；若项目已有 TavernSync 而本次角色条目缺失，按同文件现有格式补入角色卡配置。配置含特殊名称时按原名匹配，不猜测清洗名。
2. 执行最终 bundle／产物检查。任何源文件、构建产物或版本引用此后再变化，前面的验证和 push 均作废，必须重跑。
3. 主动执行 `node tavern_sync.mjs push <配置名>`；只有创建新角色、已确认需要覆盖条目差异或项目既定命令要求时才加 `-f`。
4. push 是流程最后一次目标端写入；随后只做隔离 pull／API 回读和哈希比较。stdout 成功不替代回读。若隔离 pull 得到完整 MVU 源结构，再对隔离副本重跑 `check_status_variable_bridge.mjs --variables-only`；若 pull 只导出打包字段，则改为核对四条协议等价字段、initvar 关闭状态与关键变量内容，不强造不存在的源码目录。
5. push 或回读失败时继续排错并重试，不能把任务标记完成。只有只读审查／报告任务、项目根本未采用 TavernSync、目标角色经过检查仍确实不唯一，或运行环境客观无法连接时才可跳过，并明确报告原因；单独缺少该角色的配置条目不是跳过理由。

完成条件包含“最终 push 已执行且回读通过”。若修复发生在一次 push 之后，必须再次 push 最新结果；旧 push 不算本次交付。

## 不可妥协的质量要求

- 不交付空壳、占位符、伪造数据或只改表面文案的“完成品”。
- 不凭条目数量判断世界书质量；看覆盖、职责、触发精度、因果和演绎信息。
- 不让状态栏维护第二套真相；显示数据应来自实际变量链。
- 不用正则隐藏错误协议；先修数据与输出，再做显示替换。
- 不把演示数据当运行时回退。无数据时显示等待、空态或明确错误。
- 不无条件递归、常驻、深度 0 或全蓝灯；世界书注入策略按条目职责和目标版本配置。
- 上一条不适用于本技能明确规定的 MVU 协议四条：`[initvar]变量初始化勿开` 必须显式关闭；`变量列表`、`[mvu_update]变量更新规则`、`[mvu_update]变量输出格式` 必须显式开启；四条采用蓝灯和双向递归隔离，三条运行时协议使用 system 指定深度 D0。不得把“蓝灯”误读成“启用”。精确片段见 `assets/mvu-worldbook/`，完整语义见参考 12。
- 不假定 API 名称、参数或事件；写代码前查当前类型声明。
- 不因为能联网就依赖易失 CDN；外部依赖要有版本、缓存和失败策略。
- TavernSync 实时推送角色卡前必须解析所有开场引用并绑定实际非空头像；`头像: ""`、`null` 或省略只可进入明确支持的无头像打包流程，不得直接用于当前 TavernSync 的角色 push。新卡找不到用户提供、项目已有或明确授权生成的合法头像时，停在 push 之前报告缺少头像来源；不得自行拿占位图冒充，也不得因有图像生成能力就推定用户已授权。push 后必须回读并比较开场数量与内容哈希；已有聊天首楼不会因角色定义更新而自动等同于新开场。
- 楼层状态栏必须把“所在楼层”作为一个共享上下文：等待数据、首次读取、store、刷新和写回必须复用同一个 `VariableOption`，禁止一处省略 `message_id`（默认 `latest`）、另一处使用 `getCurrentMessageId()`；store helper 只能复制并归一化该选项，不得原地修改共享对象。
- 正式界面必须多模块维护：静态 `index.html` 壳、薄入口、宿主上下文、数据 store／adapter、iframe 高度生命周期、Vue 组件和样式各有边界；不接受把正式状态栏或开局页全部塞进单个 `index.html`／`index.ts`。
- 上一条适用于所有正式美化界面，不以是否采用 MVU 为前提。纯文本解析、普通变量或无变量的展示卡也应按职责拆分；相应 adapter 可以更简单，但不能因此回退成单文件大杂烩。模块化服务于视觉打磨和稳定交互，不能成为降低审美要求的借口。
- 新建楼层状态栏优先从 `assets/status-ui-vue/` 开始；新建动态开局优先从 `assets/dynamic-opening-vue/` 开始。骨架的业务字段要按目标 Schema 替换，全部完成后才把 `OPENING_CONTRACT_CUSTOMIZED` 改为 `true`；模块边界、消息回读和高度生命周期不能删。
- 云端界面或自托管脚本每次发布必须产生稳定版本标识，并同步修改角色卡／正则／脚本库中的真实引用。禁止用 `Date.now()` 等每次加载都变化的参数冒充版本。
- 酒馆消息 iframe 的高度不能只靠固定像素或“浏览器自然撑开”。界面必须保持正常文档流，并在挂载后及内容变化时主动同步 `body.scrollHeight` 到 `frameElement.style.height`；复用项目已验证的实现或 `assets/status-ui-vue/iframe-height.ts`。
- 动态开局的成功条件不是按钮提示、前端本地状态或“已生成文件”，而是创建了正文非空的 assistant 消息、该消息携带可解析的 `data.stat_data`，并已从目标聊天回读。静态开场则必须在最终卡包 `first_mes`／`alternate_greetings` 中回读非空；动态开局卡建议提供静态失败兜底，若设计为纯动态则至少提供可诊断错误和恢复路径。

## 平台无关协作

如果宿主支持并行代理，只把相互独立的资料核对、静态审查或测试交给它们；核心架构和耦合变量链保持单一负责人。不要硬编码代理名称、模型名称或平台私有命令。

若缺少浏览器、网络或运行环境，继续完成能验证的部分，并在最终报告中准确列出“已验证”“静态推断”“未验证”，不要把环境缺失写成实现成功。对本卡已经采用的 MVU／UI 功能，缺少运行时不允许降低其静态契约：MVU 的 initvar 明确关闭、四条协议和 Schema／初值对齐；正式 UI 的多模块边界与适用检查器结果仍须完成。没有采用这些功能的卡不需要创建它们。

## 完成定义

最终交付必须同时说明：

1. 改了什么，以及关键设计为何如此；
2. 哪些文件／产物可直接使用；
3. 实际执行了哪些验证及结果；
4. 仍有哪些版本、运行环境或远端步骤未验证；
5. 是否发生了拉取、构建、导入、部署或推送。

若报告“已导入”，还必须给出目标端回读证据；若报告“界面已出现开场”，还必须说明是在新建聊天、重置首楼还是显式替换既有消息后验证。只完成 push 时写“已发送 push，尚未回读”，不得换词包装成完成。对使用 TavernSync 的新建／修改任务，未执行最终 push 本身就是未完成；目标条目缺失时先补配置，不得把 push 留给用户补做。

只在用户目标已达到、必要文件已落地且验证与限制都已如实报告后结束。
