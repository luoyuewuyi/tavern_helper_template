# Variable Structure

## 必读源

只要项目涉及 MVU 或结构化变量，先读：

1. `.cursor/rules/mvu角色卡.mdc`
2. `.cursor/rules/mvu变量框架.mdc`
3. `示例/角色卡示例/schema.ts`
4. `示例/角色卡示例/世界书/变量/变量更新规则.yaml`
5. `示例/角色卡示例/世界书/变量/变量输出格式.yaml`

不要跳过其中任何一项。
其中 rules 是硬规则；示例是结构、链路和实现方式的参考；变量具体内容按用户需求定制。

## 变量链路

变量相关实现要按这条链路理解：

1. `schema.ts`
   - 定义变量结构
   - 用 zod 4 做纠正和派生
   - 生成 `schema.json`
2. `schema.json`
   - 作为 `initvar.yaml` 等初始化文件的结构参考
3. `变量列表`
   - 告诉模型有哪些变量
4. `[mvu_update]变量更新规则`
   - 告诉模型每类变量在什么情况下允许怎样更新
5. `[mvu_update]变量输出格式`
   - 告诉模型必须用什么格式输出变量更新命令
6. 界面/脚本
   - 读取 `stat_data`
   - 按 schema 合法地展示或写入

少看其中一环，就容易把变量做坏。

## 不允许擅自更改的部分

- `变量列表` 默认不允许擅自更改结构和用途。
- `[mvu_update]变量输出格式` 默认不允许擅自更改协议、标签、块结构或命令格式。
- 这两项应优先沿用现有项目或示例中的成熟写法；如果用户没有明确要求修改，就只做引用、补齐或按现有约定生成内容。
- 需要新增变量时，优先只在 `schema.ts`、初始化数据和消费界面中补齐，不要顺手改写 `变量列表` 的既有组织方式，也不要重写 `[mvu_update]变量输出格式` 的既有协议。
- 如果用户只是要定制变量内容，允许调整变量值、字段语义和展示内容；不允许借机重构 `变量列表` 或替换变量输出协议。

## 变量界面裁剪原则

- 只要是变量系统相关界面，内容就必须以实际变量结构和实际变量用途为准。
- 不要为了“看起来完整”添加多余变量、占位变量或无实际作用的展示字段。
- 重要的变量就展示或交互，不重要的变量就减少甚至不展示。
- 变量界面的信息密度要服务游玩，不要把所有变量都堆到界面上。

## 优先级

- `.cursor/rules/mvu角色卡.mdc` 和 `.cursor/rules/mvu变量框架.mdc` 是硬规则，必须严格遵守。
- `示例/角色卡示例/...` 是结构、链路和写法的参考实现，必须认真贴近，不要自己另起一套。
- 如果示例和 rules 的理解出现冲突，以 rules 为准。
- 允许按用户需求定制变量内容、字段语义和世界观内容，但结构设计、链路拆分、schema 写法、变量规则协议要贴近示例并受 rules 约束。

## 不要改的东西

- MVU 本体脚本默认不改
- MVU 框架本身默认不改
- 如果用户没有明确要求，不要把问题转移成“去改 MVU 插件或底层脚本”

默认需要处理的是：

- `schema.ts`
- `initvar`
- `变量列表`
- `变量更新规则`
- `变量输出格式`
- 读取和展示这些变量的界面或脚本

## schema.ts 硬规则

- 只保留 `export const Schema`
- 不要把注册脚本、`registerMvuSchema(...)`、`$(() => ...)` 混进 `schema.ts`
- 使用 zod 4
- 优先对象结构，不要随手改成数组结构
- 数值优先 `z.coerce.number()`
- 动态键优先 `z.record(...)`
- 派生字段统一在 `transform` 中生成
- 需要幂等：`Schema.parse(Schema.parse(input))` 应稳定

## 什么放 schema.ts

适合放进 `schema.ts` 的：

- 数值范围收束
- 字段纠正
- 非法项过滤
- 派生字段生成
- 基于当前值即可决定的结构修正

示例：

- 依存度钳制到 0~100
- 物品数量为 0 时过滤掉
- 根据依存度生成 `$依存度阶段`
- 根据依存度限制称号数量

## 什么不要放 schema.ts

不适合放进 `schema.ts` 的：

- 依赖旧值的逻辑
- 跨阈值检测
- 禁止 AI 更新某字段
- 单次变动幅度限制
- 需要 `old_variables` 的规则

这些应优先放到 `Mvu.events.VARIABLE_UPDATE_ENDED` 等事件处理中。

## 多阶段

如果阶段由数值决定：

1. 在 `schema.ts` 里产出派生阶段字段，例如 `$依存度阶段`
2. 世界书按同一套区间或同一派生结果写阶段块
3. 界面读派生阶段字段，不自己再算一次

不要出现三套阈值。

## 变量更新规则

`[mvu_update]变量更新规则` 不是变量结构本身，它是给模型看的更新约束。

重点：

- 固定键可以合并写规则
- 动态对象要写成索引签名
- 不要给只读字段 `_变量` 写更新规则
- 变量规则要真实影响游玩，不是只做展示

## 变量输出格式

`[mvu_update]变量输出格式` 要沿用示例协议。

重点：

- 输出 `<UpdateVariable>`
- 含 `<Analysis>` 和 `<JSONPatch>`
- 使用约定的 `replace`、`delta`、`insert`、`remove`、`move`
- 不要擅自改成别的标签或别的 patch 协议

## 变量结构检查表

- 已读完上述 5 个必读源
- `schema.ts` 纯净无副作用
- zod 4 / `z.coerce.number()` / `z.record(...)` 用法正确
- 派生字段统一来源
- 旧值依赖逻辑没有误塞到 `schema.ts`
- 世界书变量规则和输出格式没有偏离示例协议
- 界面写入变量前会先过 schema 检测
