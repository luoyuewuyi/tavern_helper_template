# Style And Safety

## 手机优先

- 默认按手机界面展示做布局。
- 确保在酒馆 iframe 中宽度自适应。
- 避免横向滚动和依赖宿主高度的布局。
- 在满足信息可读性的前提下尽量缩小界面总面积。
- 优先考虑弹窗、抽屉、分栏、折叠区、分页、标签页、二级界面等分层方案。
- 不要把低频信息和高频操作全部堆在首屏。

## 主题与美化

- 配色、材质、字体、动效围绕题材服务。
- 在实用基础上优先保证观感，界面需要先好看，再谈克制。
- 可以参考在线视觉案例、成熟产品界面或同题材作品做法，但不要机械照抄。
- 可以做美化和特效，但不要盖过叙事主题。
- 状态栏、信息面板、弹窗、标签风格要与世界观一致。
- 状态栏默认只显示当前已有的关键基础信息，例如姓名、性别、身份、等级、境界、生命/体力、金币/资源、装备、背包、关键状态、关系数值等；按题材取舍即可。它是当前 user 状态的游戏面板，不预测、不安排、不替 user 决定下一步。
- 除非用户明确要求剧情型状态栏，不要把剧情线路、任务指引、下一步选择、当前行动、目标、悬念推进、作者提示、教程说明或大段世界观说明塞进状态栏。
- 状态栏互动只适合确定可执行的一次性操作，例如装备/卸下装备、切换功法、运转/停止功法、使用道具、消耗资源、尝试突破、领取/查看背包物品。不要把目标、计划、当前行动或下一步建议做成状态栏字段或按钮。
- 美化界面状态栏与纯文字状态栏互斥：已有前端界面/正则加载的美化状态栏时，只输出界面占位标签，不要再同时附加纯文字状态栏代码块；没有美化界面状态栏时，纯文字状态栏才使用三反引号代码块。
- 界面应精干、直接、好看，不要做成带强烈说教意味的“引导页”。

## 变量安全

- 先读现有 schema、变量规则、输出格式。
- 明确哪些字段是展示字段，哪些字段是驱动剧情的规则字段。
- 可增补，不乱改原有字段含义、路径和协议名。
- 如果变量内容天然适合交互，例如装备、背包、商店、任务、日志、地图或角色关系，可以优先设计交互式界面。
- 在实现变量交互前先确认用户意图，尤其是哪些操作允许在界面里直接修改变量，哪些只能展示不能改。
- 不要默认给变量增加“当前事件进度”之类的追踪字段；只有项目明确存在专门的多阶段或故事线控制需求时才考虑增加。

## 输入界面

- 任何需要用户输入内容的界面，默认优先自由填写，而不是强制预设选项。
- 如果加入预设选项，它们应只是辅助输入，不能堵死玩家自定义空间。
- 开局界面、角色设定界面、背景设定界面、商店备注界面等都遵守这条规则。

## 正则安全

- 不先写替换内容再倒推匹配规则。
- 先确认标签，再确认匹配式，再确认渲染内容。
- 捕获组 `$1`、`$2` 的语义必须与正则一一对应。

## 实现纪律

- 先读规则和示例，再写代码。
- 先最小改动复用现有项目，再考虑重构。
- 凡是界面项目，必须 `pnpm build`。
- 不把未构建源码交付给用户当最终结果。
- 任何界面最终产物都要保持完整 HTML 结构，不要为了图省事只交局部片段。
- 不替用户执行最终 push；交付停留在本地可检查、可手动推送的状态。
