# Worldbook Rules

## 必读基线

只要任务涉及世界书，先读：

1. `自制文件放置处/世界书制作要求（变量不需读取）.txt`
2. 当前任务相关的 `自制文件放置处/角色制作指南/` 文件，例如角色基础、三面性、性格调色盘、二次解释、nsfw 调色盘等。
3. 当前项目已经存在的世界书、角色设定、变量协议和输出格式。

其中：

- `自制文件放置处/...txt` 是配置和拆分要求的硬基线。
- `角色制作指南/` 是角色塑造、行为化描写、人物层次和表达方式的硬基线；不要只读世界书规则就开始写角色相关条目。
- 不要默认引用仓库内其他成品项目作为世界书参考。除非用户明确点名要求参考某项目，否则只围绕当前项目和自制文件规则制作。

## 常见条目

按项目需要组合这些内容：

- 世界观和玩法规则
- 角色速览
- 角色详细条目
- 场景和事件条目
- 正则替换配置

以下内容属于变量文件或配置文件，不应混入普通世界书设定条目：

- 变量初始化
- 变量列表
- 变量更新规则
- 变量输出格式
- UI 制作提示词、作者工作流、文件放置说明、调试说明

## 蓝灯 / 绿灯 / 指定深度

- 蓝灯：常驻规则、核心玩法、固定输出协议。
- 绿灯：按关键字触发的角色、场景、事件、详细设定。
- 指定深度：只在仓库既有规则明确需要时使用，尤其是系统级格式和高优先级约束。

## 默认规则表

以下是默认分配规则，不是死模板。先按它判断，再根据项目实际情况微调：

- 世界观总设定、核心玩法、演绎规则：优先蓝灯；若属于强制系统格式或必须持续生效的高优先级规则，可改为指定深度。
- 角色速览、条目索引、触发提示：通常蓝灯，但它们的职责是提示和激活绿灯条目，不是替代绿灯详细条目本身。
- 角色详细档案、NPC 详细信息、场景细节、事件细节：通常绿灯。
- 状态栏格式、固定回复格式、必须每轮都知道的系统硬规则：通常指定深度。
- 变量初始化、变量列表、变量更新规则、变量输出格式：放入变量文件夹或项目既有变量协议条目，优先沿用示例和现有项目约定，不混入世界设定正文。
- 正则替换条目：按功能常驻，不靠角色触发逻辑去判断。

## 使用方式

- 先用规则表做第一判断。
- 再根据项目情况发挥，不要机械照抄。
- 发挥的是内容，不是放弃配置。世界书必须写到可直接交付的完成度，不能只给概括、提纲或“后续再补”的半成品。
- 如果一个项目本身体量很小、角色很少、记忆压力不高，更多内容用蓝灯也可能没问题。
- 如果项目角色多、场景多、细节多，就应该更多使用绿灯分流，避免全部常驻。
- 重点不是“严格套配置模板”，而是让条目激活方式和内容用途匹配。

## 速览条目

- 速览类条目是给 AI 一个“目录”和“触发提示”，帮助它在合适的时候激活绿灯详细条目。
- 速览条目只需要汇总绿灯条目的关键词和简短用途说明。
- 速览条目不能承担绿灯详细条目的内容量，不要把详细设定塞进速览里。
- 速览条目的核心作用是“告诉 AI 有哪些绿灯条目、什么时候该触发”，不是“用一个蓝灯条目替代所有绿灯条目”。
- 如果项目是多角色卡或多场景卡，速览尤其重要；它应该像词典或目录，而不是正文设定本体。

## 来自自制要求的硬规则

- 世界书描述尽量客观，不要写成强主观评价或作者说教。
- 角色内容是否展开，按角色重要性判断；重要角色写细，不重要角色可以收敛，但最好保留基础介绍。
- 除非用户明确要求，否则不要顺手做状态栏。
- 在保证质量的前提下，尽量压低 token 消耗。
- 角色速览只需要围绕绿灯条目组织内容，用于更好激活绿灯条目。
- 所有角色、地点、种族等不常用的详细设定，应拆成单独世界书条目，而不是塞进速览。
- 世界观设定通常不要压成一个条目，除非内容很少；应按地点、种族、物品、规则等分类拆分。
- 多条目优于全挤一起，但也不要拆得过散；拆分颗粒度要服务记忆判断。
- 关键字用数组格式，不用逗号字符串。
- 所有世界书条目默认都要勾选“不可递归”和“防止进一步递归”，蓝灯和绿灯都一样；这不是可选优化，而是默认配置。
- 除非明确需要，否则不要乱用指定深度。
- 如果使用指定深度，必须用正确配置：`类型: 指定深度`、`角色: 系统`、并填写 `深度`。
- `类型: 深度` 是错误写法，必须改成 `类型: 指定深度`。
- 使用指定深度时，深度范围按 `0-4` 理解，数值越小越靠近当前对话、优先级越高。
- 无论蓝灯还是绿灯，递归相关限制都应按要求配置，避免 token 爆炸和条目互相误激活。
- 世界书条目插入位置常用两种：`角色定义之前`（默认）、`指定深度`（角色: 系统，用于状态栏等高优先级输出协议）。不要随便发明其他插入位置。
- 多角色项目默认顺序意识参考：世界观/规则在前，场景/事件中段，核心角色详细条目后置于 `99` 左右，NPC 再后置于 `100` 左右。
- 速览条目通常放在世界观和基础规则之后、详细角色条目之前，承担”目录”和”触发提示”作用。
- 后续调整只允许基于现有成品做新增、修改、删除；不要留下”待补充””略””同前””见上文”这类占位式内容。

## index.yaml 结构硬规则

- **禁止文件夹嵌套**：`条目:` 下只能有一层 `文件夹:` → `条目:`，不能在文件夹内再嵌套文件夹。同步脚本 `tavern_sync.mjs` 的 schema 不支持嵌套文件夹结构，会直接报”无效输入”。
- 如需分组，用 `===分组名===` 分隔符条目（`<<: *分隔符`）做视觉分割，所有实际条目平铺在文件夹内。
- 文件系统中可以保留子目录组织（如 `世界书/角色/黑月铁骑/玄月.yaml`），`文件:` 字段引用时写完整相对路径即可，但 index.yaml 的条目结构必须平铺。
- **第一条消息的 `文件:` 用反斜杠、不带扩展名**（如 `第一条消息\0`，引用 `第一条消息\0.txt`）。这是全仓库统一格式，不要用正斜杠或带 `.txt` 扩展名。
- **index.yaml 顶层可选字段（头像、版本、作者、备注）用空字符串 `''`，不要用 `null`**。`null` 在 schema 校验时可能导致整个角色卡元数据被丢弃，只导入世界书。

## 顺序与递归

- 顺序越小越先加载。
- 状态栏或核心输出协议通常要放在高优先级位置。
- 递归设置遵守项目现有约定；如果已有统一模板，沿用模板。
- 如果没有现成模板，就默认所有条目都开启“不可递归”和“防止进一步递归”。
- 多角色世界书默认顺序可参考：
  - `1-20`：世界观总则、赛事体系、演绎规则等常驻基底
  - `20-40`：速览、图鉴、索引类蓝灯条目
  - `80-98`：场景、事件、功能性绿灯条目
  - `99`：核心角色详细条目
  - `100`：NPC、配角集合或次级角色条目
- 这不是死模板，但如果没有更合理的项目特例，就先按这个思路组织。

## 成品级拆分标准

世界书至少先判断是否需要这些层：

- `世界总则`：世界名、核心设定、玩法基底、时代背景、关键机制。
- `演绎规则`：叙事要求、互动要求、输出习惯、演出边界。
- `角色总览`：只做目录、关键词和简短用途说明，用来触发绿灯角色条目。
- `角色详细条目`：核心角色单独成条，重要角色不要挤在合集里。
- `配角集合/图鉴/体系条目`：中低权重信息按主题聚合，但仍要保证能被正确调用。

制作时先问自己：

- 这个信息是常驻基底，还是应按关键词触发？
- 这个角色是否重要到值得单独成条？
- 这个设定是应该进总则，还是应拆到图鉴、体系、地点、物品或 NPC？
- 速览是否真的只承担触发提示，而没有偷塞详细设定？
- 当前条目是最终可交付内容，还是只是作者笔记？

如果最后更像“摘要”“策划提纲”或“脑图备注”，那就还没达到成品要求。

## 变量相关条目

若项目使用变量，通常需要：

- `[initvar]变量初始化勿开`
- `变量列表`
- `[mvu_update]变量更新规则`
- `[mvu_update]变量输出格式`

若已有这些条目，优先复用并增补，不要重写协议名。
- `变量列表` 和 `[mvu_update]变量输出格式` 默认不允许擅自更改；如果项目已有现成版本，应保持其结构、用途和协议稳定。

## 变量结构检查表

只要改 `schema.ts` 或新增变量结构，先按这张表检查：

- 是否已经重新读取 `.cursor/rules/mvu角色卡.mdc`、`.cursor/rules/mvu变量框架.mdc` 与示例 `schema.ts`
- 是否使用 zod 4，而不是其他写法
- 是否优先使用对象和 `z.record(...)`，而不是数组索引结构
- 是否把 `schema.ts` 保持为纯 `export const Schema`，没有注册脚本副作用
- 是否考虑增量更新与幂等性
- 数值字段是否优先用了 `z.coerce.number()`
- 派生字段是否放在 `transform` 中统一产出
- 默认值策略是否和 rules 一致，而不是随手改写

没有过这张检查表，就不要提交变量结构。

## 多阶段

如果项目有角色阶段、关系阶段、成长阶段或剧情阶段：

- 先参考 `示例/角色卡示例/世界书/角色/角色阶段.yaml`
- 再参考 `示例/角色卡示例/schema.ts` 里的派生阶段字段
- 再确认状态栏或界面如何消费这个阶段结果

多阶段的最低要求：

- 阶段必须有清晰触发条件，通常来自变量区间或派生值
- 每个阶段必须有真实行为差异、叙事差异或规则差异
- 阶段条目、变量结构、界面展示三者要互相对得上
- 若阶段由数值变量决定，先在 `schema.ts` 中产出派生阶段字段，再让界面读这个字段
- 世界书中的阶段块切换要直接绑定数值区间或唯一派生结果，不能写成模糊“高了就进入下一阶段”

推荐链路：

1. 在 `schema.ts` 中根据数值变量计算派生阶段字段，例如 `$依存度阶段`
2. 在世界书阶段条目中按示例做区间判断或消费同一套阶段结果
3. 在状态栏或界面中读取派生阶段字段展示

这样做的目的：

- 阈值只维护一套
- 世界书行为和界面展示不会错位
- 不会出现变量已经到下一阶段，但界面或世界书还停在旧阶段的错误

禁止做法：

- 只写几段空泛阶段描述，不绑定变量条件
- 只在世界书里写阶段名，却不让界面或状态栏读取
- 用临时口头规则代替正式的阶段结构
- 在组件、脚本、世界书中各自维护不同的阶段阈值

## 正则链路

若界面依赖标签渲染，世界书中必须明确：

- 标签名
- 输出位置
- 是否每次回复都要输出
- 与变量更新块的相对顺序

正则中必须明确：

- 匹配表达式
- 来源范围
- 仅格式显示还是仅提示词
- 最终替换内容

如果是开局界面，还必须明确：

- 开局标签名固定为 `【开局界面】`
- 只在第一次初始化时消费
- 提交结果写到哪里：后续消息、世界书还是初始变量
- 若写入变量，检测失败时如何回退到合法值

## 关键约束

- 不把所有设定挤成一个大条目，按作用拆分。
- 也不要拆得失去上下文，保持中等颗粒度。
- 关键字使用数组格式。
- 没有必要时不要新增“深度”条目。
- 有变量时，除了显示变量，还要让变量规则真实影响游玩。
