# Workflow

## 默认顺序

1. 读取 `.cursor/rules`、`示例`、`初始模板`、`自制文件放置处`、`tavern_sync.yaml`。
2. 读取 `package.json`、`webpack.config.ts`、`@types/`、`slash_command.txt`、`util/` 和 `README.md` 中与当前需求直接相关的部分。
3. 检查 `tavern_sync.yaml` 是否已有对应项目配置。
4. 若没有，先补写配置；若有，直接继续。
5. 如 `src` 中存在其他项目，优先执行 `pnpm stage:card -- <项目名>`，确保 `src` 只保留当前项目。
6. 执行 `node tavern_sync.mjs pull <项目名>`。
7. 检查 `src/<项目名>/index.yaml` 及其 `界面/`、`脚本/`、`世界书/` 子目录。
8. 判断需求范围，只改所需部分。
9. 若存在界面或界面注入链路，执行 `pnpm build`。
10. 整理好本地结果，交由用户手动 push 或导入。

如果需求涉及变量、多阶段、状态栏、正则或开局界面，必须先读 `示例/角色卡示例` 的对应实现，再决定改法。

## 修改策略

- 先兼容现有项目结构，再增补。
- 尽量复用现有 `schema.ts`、正则、世界书条目和界面骨架。
- 不要因为用户新增一个界面，就重写整张角色卡。
- 涉及“多阶段”时，先确认示例里的阶段链路，再实现；不要凭印象简化。
- 在 Windows 下如果补丁、命令或生成内容明显偏长，默认直接拆成两个或多个步骤执行。
- 先拆文件，再拆段落，再拆 patch；不要等长度报错后才开始拆。
