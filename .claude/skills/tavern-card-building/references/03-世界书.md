## 核心原则

世界书不是资料仓库，而是按场景把“此刻需要的事实和演绎规则”送进上下文的检索系统。质量由覆盖、职责、触发精度、注入位置、因果和实际演绎效果决定，不由文件数或总字数决定。

## 先做覆盖矩阵

按卡的玩法选择需要的维度，不必机械填满所有类别：

| 维度 | 要回答的问题 |
| --- | --- |
| 世界规则 | 哪些规律与现实不同，违反后会怎样 |
| 地点 | 场景有什么资源、危险、秩序和可互动对象 |
| 组织／阵营 | 目标、手段、冲突、层级、对用户和角色的态度 |
| 核心人物 | 欲望、秘密、能力、关系、压力下行为 |
| 社会与文化 | 礼仪、禁忌、阶层、经济、法律、媒体如何影响选择 |
| 能力／系统 | 获得、使用、限制、代价、反制、成长 |
| 事件／任务 | 触发、参与者、阶段、分支、失败后果 |
| 关系 | 证据、门槛、冲突、修复、不可逆变化 |
| 风格／演绎 | 叙述规则、信息限制、特殊场景写法 |
| 变量协议 | 初始值、更新条件、输出格式、当前值注入 |

对每个维度标记：已有、缺失、重复、冲突、只需按需触发。覆盖矩阵是规划工具，不是条目目录。

## 一条一职责

一条世界书应有清楚的检索意图。判断标准：它能否用一句话说明“何时需要，以及注入后改变模型什么行为”。

可以合并：总是同时出现、共享同一触发语境、拆开会失去因果的内容。

应该拆分：触发关键词不同、注入位置不同、保密级别不同、只有部分场景需要、单条过大导致无关内容频繁进入上下文。

不要把同一个角色的所有资料盲目拆成十几个短条目，也不要把整个世界塞进一个常驻长条目。

## 用因果写内容

每条优先包含对演绎有用的链路：

1. **是什么**：事实或规则；
2. **为何存在**：历史、动机或机制；
3. **如何运作**：触发、过程、参与者；
4. **限制与代价**：不能做什么，失败会怎样；
5. **可观察表现**：角色如何知道，场景如何呈现；
6. **演绎要求**：模型在相关场景应保持什么一致性。

如果一条只有“某组织很强大”，它几乎不能指导剧情。补充它为何强、如何使用力量、内部矛盾、外部反制和用户可能遇到的具体后果。

## 常驻与按需触发

### 常驻条目

只放每轮都必须知道且足够紧凑的信息：世界核心差异、角色关系前提、关键输出协议。常驻内容太多会挤压对话和按需资料。

### 关键词触发条目

适合地点、人物细节、组织、物品、任务和事件。关键词必须是对话中实际可能出现且歧义可控的表达。

不要因为关键词难配就把条目改成常驻。先改条目职责、关键词组合或触发方式。

### 向量／语义检索

适合用户表达变化大、资料量大且运行环境支持的项目。仍要测试召回与误召回；语义检索不是无需设计条目的理由。

## 关键词设计

- 使用真实称呼、别名、地点名、事件名和稳定短语；
- 避免单独使用“她”“城市”“任务”等高频泛词；
- 同义词只加入确有召回价值的形式；
- 同角色多条资料可共享身份关键词，但用次级关键词或条件缩小触发；
- 检查大小写、全半角、语言别名和拼写变体；
- 关键词字段的分隔格式以当前项目规范为准。

为每条准备三个样例：应触发、不应触发、边界情况。实际在目标版本中测试，而不是只看配置。

## 注入位置与顺序

注入位置决定信息如何被模型理解：

- 角色定义前：更像世界与系统背景；
- 角色定义后：更贴近人物、场景和当轮行为；
- 指定深度：适合必须靠近最近对话的协议、摘要或控制信息；
- 示例对话或其他位置：仅在项目明确需要时使用。

没有通用的固定顺序编号。先读当前模板和本技能契约，按“基础规则 → 当前场景 → 当前角色／事件 → 输出协议”的依赖关系安排；不要翻找任意角色卡猜规范。深度 0 很强，不应作为普通内容的默认位置，但控制协议确有可能需要它。

## 递归

递归控制是否允许条目内容继续触发其他条目，以及是否能被其他条目触发。不同版本和模板字段名称可能相反或拆分，必须查当前配置。

使用递归的合理情形：

- 一个概览条目有意引出若干细节；
- 事件条目明确依赖地点或组织条目；
- 项目经过测试，用递归构建受控知识链。

关闭递归的合理情形：

- 防止关键词在条目正文中形成触发风暴；
- 输出协议、变量说明等元信息不应扩散；
- 条目已包含足够上下文；
- 当前模板的推荐配置如此。

不要给普通剧情条目全局套用“两个递归开关必须都为某值”。画出预期触发链，并测试循环、重复和令牌膨胀。MVU 四条协议是明确例外：为避免协议相互激活，它们必须同时设置 `不可被其他条目激活: true` 与 `不可激活其他条目: true`。

## 保密与视角

世界书进入模型上下文后，不代表场内角色应知道全部内容。对秘密资料明确：

- 谁知道、谁怀疑、谁不知道；
- 通过什么证据才能获知；
- 模型可以用于叙事规划但不能让角色直接说出的内容；
- 泄露后会产生什么后果。

若严格保密很重要，使用分条触发、条件控制或脚本注入，不把秘密塞进永久常驻角色描述。

## MVU 相关条目

变量卡常见的系统条目包括初始变量、当前变量列表、更新规则和输出格式。它们是协议，不应与普通剧情百科混写。

- Schema 是字段和类型的权威来源；
- `[initvar]变量初始化勿开` 只提供真实初值，必须显式 `启用: false`；它保留蓝灯配置不代表默认开启；
- 更新规则描述何时改、改多少、哪些字段不可由模型改；
- 当前变量注入只包含模型需要的状态；
- 输出格式确保更新块与显示占位符稳定生成。

中文 TavernSync 索引的强制配置如下：

| 条目 | 启用 | 激活 | 插入位置 | 双向禁止递归 |
| --- | --- | --- | --- | --- |
| `[initvar]变量初始化勿开` | `false` | 蓝灯 | 角色定义之前 | 是 |
| `变量列表` | `true` | 蓝灯 | system 指定深度 D0 | 是 |
| `[mvu_update]变量更新规则` | `true` | 蓝灯 | system 指定深度 D0 | 是 |
| `[mvu_update]变量输出格式` | `true` | 蓝灯 | system 指定深度 D0 | 是 |

四条的可复制片段位于 [`../assets/mvu-worldbook/index-fragment.yaml`](../assets/mvu-worldbook/index-fragment.yaml)。Schema 非空时 initvar 内容不得是空对象；`变量列表`、更新规则和输出格式也必须绑定各自可读、非空的文件。完整原因、原始卡等价字段和动态开局事务见 [`12-MVU世界书与开局契约.md`](12-MVU世界书与开局契约.md)。

具体实现见 [`04-MVU变量系统.md`](04-MVU变量系统.md)。

## 令牌预算

评估四项而不是只看原始字数：

- 常驻条目的固定成本；
- 典型场景同时触发多少条；
- 单条触发后带入多少无关内容；
- 递归或重复事实造成的额外成本。

优化顺序：删除重复 → 缩小职责 → 改善关键词 → 调整常驻／按需 → 精炼表达。不要先把所有条目压成失去因果的关键词列表。

## 验证

至少完成：

1. 所有引用文件存在且非空；
2. 配置能被目标工具解析；
3. 应触发／不应触发样例通过；
4. 同一事实没有互相冲突的权威来源；
5. 典型场景的注入量可接受；
6. 模型能据此表现限制、代价和后果；
7. 秘密没有无条件泄露；
8. 更新协议不会被普通世界书内容误触发。

审查脚本可以报告文件数量、长度和疑似配置问题，但短条目不一定薄，长条目不一定好。最终结论必须回到条目职责和实测。
