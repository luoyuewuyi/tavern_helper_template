# 多模块界面工程规范

## 目标优先级

本规范的第一目标不是“代码看起来工程化”，而是让最终状态栏、开局页和楼层界面比纯文本更美观、更有氛围、更易读、更顺手。多模块与可维护性用于支撑视觉细化、交互打磨和反复迭代；如果最终界面粗糙、拥挤、缺少层级或像默认后台表单，即使目录完整也不算合格。

“是否使用 MVU”和“是否多模块”无关。正式美化界面默认多模块，数据源可以是：

- 纯文本或标签解析；
- 普通聊天／消息／角色变量；
- 脚本实时计算；
- MVU `stat_data`；
- 无变量的静态开局／说明界面。

MVU 只是某些界面的数据源，不是多模块架构的触发条件。只有一次性最小复现、明确要求的极简片段或纯文字状态栏可以单文件。

## 适用范围

本页适用于正式交付的状态栏、开局配置、阅读器、楼层游戏 UI、消息内控制面板及由脚本创建的复杂 iframe。一次性复现页可以临时单文件，但进入角色卡、发布或长期维护前必须拆分。

“打包后只有一个 `index.html`”不等于“源码可以只有一个文件”。单产物是部署选择；源码仍须有清楚边界，才能审查变量链、替换宿主 API、测试高度和修改组件。

## 不可退让的源码边界

正式界面至少应分离：

1. `index.html`：纯静态挂载壳；
2. `index.ts`：只做初始化编排；
3. `context.ts`：所在楼层、作用域、版本等宿主上下文；
4. `store.ts`／`adapter.ts`：读取、校验、刷新和显式写操作；
5. `iframe-height.ts`：高度测量、Observer 和清理；
6. `App.vue`：组合页面级组件；
7. `components/`：按信息职责拆分组件；
8. 全局样式与组件 scoped 样式。

禁止以下正式实现：

- 在 `index.html` 内同时放大量 HTML、CSS、脚本和宿主 API；
- `index.ts` 同时承担变量兼容、业务逻辑、DOM 生成、样式字符串和事件清理；
- 每个 Vue 组件直接调用 `getVariables`、`Mvu`、`parent` 或 Slash Command；
- 用 `document.getElementById` 查找业务节点；同一界面可能在多个历史楼层同时存在，应使用组件 ref 或当前根容器内的查询；
- 组件维护一份与真实 `stat_data` 分离的持久化副本；
- 把 mock 数据作为读取失败后的生产回退。

## 推荐目录

```text
界面/状态栏/
├─ index.html
├─ index.ts
├─ App.vue
├─ context.ts
├─ store.ts
├─ iframe-height.ts
├─ global.css
├─ adapters/             # 只有兼容旧字段／多数据源时增加
├─ actions/              # 只有明确写操作时增加
└─ components/
   ├─ StatusShell.vue
   ├─ WorldSummary.vue
   └─ CharacterSummary.vue
```

目录不要求机械一致，但职责必须等价。小界面可以只有一个业务组件；不能因此删除 context、store 和高度生命周期边界。

## 入口与静态壳

`index.html` 只保留打包器要求的空 `head` 和挂载节点：

```html
<head></head>
<body>
  <div id="app"></div>
</body>
```

入口只编排，不写业务 UI：

```ts
import { waitUntil } from 'async-wait-until';
import App from './App.vue';
import { variableOption } from './context';
import { installIframeHeightSync } from './iframe-height';
import './global.css';

$(errorCatched(async () => {
  await waitGlobalInitialized('Mvu');
  await waitUntil(() => _.has(getVariables(variableOption), 'stat_data'));

  createApp(App).use(createPinia()).mount('#app');
  await nextTick();
  installIframeHeightSync();
}));
```

不要使用 `DOMContentLoaded`：远程 HTML 常由 `$('body').load(...)` 注入，此时该事件不会再次触发。沿用项目的 `$(() => ...)`／等价加载钩子。

## 数据与宿主适配

本节示例以 MVU 楼层变量展示完整边界；非 MVU 界面仍保留等价职责，但实现可更轻：纯文本状态栏用 `parser.ts`／`adapter.ts`，普通变量用对应 `store.ts`，静态开局用只读 model。不得因为没有 MVU 就让组件直接解析全局 DOM、把样式和事件塞回 `index.ts`。

楼层状态栏在 `context.ts` 只计算一次消息号：

```ts
export const messageId = getCurrentMessageId();
export const variableOption = Object.freeze({
  type: 'message',
  message_id: messageId,
} as const satisfies VariableOption);
```

等待条件、store、刷新和写回都导入这个对象。省略 `message_id` 会默认读 `latest`，不能与当前楼层 store 混用。

消费者必须把共享对象视为只读。若 store helper 需要把 `'latest'` 归一化为 `-1`，先用展开运算复制内部选项，禁止原地修改 `context.ts` 导出的对象；否则冻结对象会在 ES module 严格模式抛错，未冻结时也会让其他消费者悄悄换目标。

`store.ts` 负责 Schema 校验和响应式同步；`adapters/` 只把旧字段映射成当前只读视图，不反向创造第二套真相。写操作收口为命名 action，写清允许修改的路径、失败行为和重复点击策略。展示组件只消费 props／store 视图。

动态开局必须再分离 `actions/start-game.ts` 与 `adapters/message-adapter.ts`：前者执行表单校验、0 层变量深拷贝、字段映射和事务编排；后者只封装 `createChatMessages`／消息回读。组件不得把“点击事件已返回”当成功，只有回读到正文非空、角色为 assistant、携带正确 `data.stat_data` 的新消息后才切换主界面。完整契约见 [`12-MVU世界书与开局契约.md`](12-MVU世界书与开局契约.md)。

## iframe 自动撑高

酒馆助手当前维护者实现的核心协议是：读取 `body.scrollHeight`，写入 `frameElement.style.height`，并以 `ResizeObserver` 观察 `body`。正式项目应复用本项目已验证的 helper；没有现成 helper 时使用本技能资产 [`../assets/status-ui-vue/iframe-height.ts`](../assets/status-ui-vue/iframe-height.ts)。

实现要求：

- 挂载并 `nextTick` 后做首次测量；
- 通过 `requestAnimationFrame` 合并同一帧的多次通知；
- 观察 `body` 的尺寸变化，异步列表、tab、折叠、字体和图片变化后能再次测量；
- 高度取有限正数并向上取整，仅在变化超过 1px 时写回；
- `pagehide` 时断开 Observer 和事件；
- 无法访问 `frameElement` 时清楚 no-op，不跨域猜测父页面协议。

根布局必须保持正常文档流。`html/body/#app` 使用 `height: auto`；禁止 `100vh`、根级固定高度、根级 `height/min-height: 100%`、主体全绝对定位。否则 body 高度会被宿主反向约束，产生截断或 ResizeObserver 反馈循环。

## 组件与样式

按信息职责拆分，不按“每 20 行一个组件”机械拆分。一个组件应有明确输入、空态和交互责任。页面级 `App.vue` 只组合组件和少量页面状态；业务组件不读取全局宿主对象。

样式约束：

- 全局文件只放 reset、主题 token、body／app 基线；
- 组件细节使用 scoped 样式；
- 避免全局标签选择器污染酒馆；
- 宽度响应式，长文本可换行，移动端不产生横向滚动；
- 根容器不建立第二层全页滚动；大量条目的业务列表才使用有上限的内部滚动；
- 动效尊重 `prefers-reduced-motion`，不可影响高度测量稳定性。

### 视觉质量完成门

根据题材建立明确视觉方向，而不是套统一紫色卡片模板。至少完成：

- 主题、材质感、色彩和字体气质与角色／世界一致；
- 主次信息一眼可辨，核心数值／关系／风险有视觉焦点；
- 留白、密度、对齐、圆角、边框、阴影和分隔语言一致；
- 图标使用统一图标体系，不用 emoji 冒充界面图标；
- 默认态、空态、加载态、错误态、禁用态和交互反馈都经过设计；
- 动效强化反馈与氛围，不用无意义常驻闪烁；
- 窄屏重新组织信息，不只是把桌面界面等比压窄；
- 长文本、极端数值、零数据和多角色数据不会破版。

交付前必须在浏览器检查真实画面并保存／查看桌面与移动端截图。视觉检查与变量链、构建检查同级；不能只凭 DOM 存在或测试通过判断“美化完成”。

## 云端版本与缓存

本节说明“已经获得远端发布授权之后”如何做版本和缓存治理，不自动授予 Git push、CDN 上传、公开发版或修改线上资源的权限。用户只说“构建”“打包”“导入角色卡”不等于授权公开发布；没有明确授权时完成本地构建、生成待发布产物与引用清单，并把远端步骤标为未执行。

发布 URL 必须可识别实际版本。首选不可变标签／提交：

```js
$('body').load(
  'https://cdn.jsdelivr.net/gh/owner/repo@v1.4.2/dist/card/ui/status/index.html',
);
```

若工作流必须从可变分支读取，至少用每次发布递增的稳定查询参数：

```js
$('body').load(
  'https://testingcf.jsdelivr.net/gh/owner/repo/dist/card/ui/status/index.html?v=1.4.2',
);
```

版本号必须来自一次发布，而不是一次页面加载。禁止 `Date.now()`、随机数和无版本裸分支 URL。推荐把角色卡顶层 `版本` 作为发布版本源，构建期把同一值写入 UI 的 `data-ui-version`／控制台标记，并在最终正则引用中使用同一版本。

发布闭环：

1. 递增版本；
2. 构建并检查产物；
3. 上传／推送对应产物；
4. 更新 `index.yaml` 正则和脚本库的真实 URL；
5. bundle／导出新卡；
6. 直接请求最终 URL，确认状态码、内容和版本标记；
7. 在酒馆新开 iframe 验证，不拿旧已加载 iframe 当证据。

## 生命周期与验证

初始化、事件、轮询、Observer 和写操作各自有单一所有者。`pagehide` 清理宿主事件、定时器和 Observer；不要依赖组件恰好被 GC。

至少验证：首次加载、历史楼层、最新楼层、生成后刷新、swipe、tab 展开／收起、异步长列表、窄屏、字体放大、离线资源、重载和重复挂载。高度测试同时检查“能长高”和“能回缩”，并确认父消息没有双滚动或大片空白。再用桌面／移动截图检查视觉层级、密度、题材氛围和交互状态；发现只是“能用但不好看”时继续迭代。

正式交付前运行 `check_frontend_structure.mjs <角色卡目录>`。它用于阻止单文件源码、组件直连宿主 API、楼层读取不一致、缺少主动高度同步、根级 `100vh`／固定高度和生命周期清理缺失。构建产物即使被内联成一个 HTML，也必须回到源码目录完成这项检查。
