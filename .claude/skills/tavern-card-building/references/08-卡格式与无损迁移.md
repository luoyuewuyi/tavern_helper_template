## 目标

编辑 PNG、JSON、CHARX 或历史卡时，默认目标是“只改变用户要求的内容，其余字段、扩展和资源可往返保留”。格式迁移不是重新抄一遍可见字段。

规范基线：

- [Character Card V2 Specification](https://github.com/malfoyslastname/character-card-spec-v2/blob/main/spec_v2.md)
- [Character Card V3 Specification](https://github.com/kwaroran/character-card-spec-v3/blob/main/SPEC_V3.md)
- [SillyTavern 官方角色字段与导入导出说明](https://github.com/SillyTavern/SillyTavern-Docs/blob/main/Usage/Characters/index.md)

目标 SillyTavern 版本与其实际导入器仍是最终兼容基线。

## 先识别容器，不信扩展名

- 读取文件魔数和容器结构；不要因为文件叫 `.zip`、`.png` 或 `.json` 就直接选择解析器。
- PNG／APNG 既是图像也是元数据容器；普通图像重编码可能丢失角色卡块。
- CHARX 本质是 ZIP 容器；先列出成员并检查根目录 `card.json`，不要直接全部解压覆盖工作区。
- JSON 先读取 `spec`、`spec_version` 和顶层结构，再判断 V1／V2／V3 或应用私有格式。
- 保留原文件和哈希；修改输出到新文件，验证后再按用户要求替换。
- 扩展名与魔数不一致是失败，不是警告。例如 `.png` 实际以 `{` 开头时，它仍是错命名的 JSON，不能交给 PNG 导入器后声称“卡包已生成”。

## 版本速览

### V1

V1 是平铺对象，核心字段为：

```text
name, description, personality, scenario, first_mes, mes_example
```

历史卡可能另带未标准化字段。不要只按这六项重建后丢弃其他数据。

### V2

V2 使用：

```text
spec: chara_card_v2
spec_version: 2.0
data: { ... }
```

`data` 包含 V1 字段，并增加 `creator_notes`、`system_prompt`、`post_history_instructions`、`alternate_greetings`、可选 `character_book`、`tags`、`creator`、`character_version` 和 `extensions`。

重要约束：

- `extensions` 以及角色书／条目内的 `extensions` 必须无损保留未知键；
- `creator_notes`、`tags`、`creator`、`character_version` 属于元数据，不应被当作提示词正文；
- `system_prompt` 和 `post_history_instructions` 的空值与覆盖语义不同，且支持 `{{original}}`；迁移时不要擅自拼接成另一段系统提示；
- `alternate_greetings` 是首条消息的额外 swipe；
- `character_book` 是随卡携带的角色专属 Lorebook。

### V3

V3 使用 `chara_card_v3`／`3.0`，在 V2 基础上增加或调整：

- `assets`
- `nickname`
- `creator_notes_multilingual`
- `source`
- 必需的 `group_only_greetings` 数组
- `creation_date`／`modification_date`
- V3 Lorebook 的 `use_regex` 等字段

V3 允许未来版本增加字段。读取时不因未知字段拒绝整张卡；编辑器应尽可能原样保留，应用私有数据放在命名空间化的 `extensions` 中。

## PNG／APNG

V3 规定：

- V3 JSON 以 UTF-8 JSON → base64 的形式放入名为 `ccv3` 的 PNG／APNG `tEXt` 块；
- 同时存在 `chara` 与 `ccv3` 时，V3 兼容应用应优先读取 `ccv3`；
- `chara` 可作为 V2 回填兼容层，但不能静默假装所有 V3 功能都已保留；
- 还可能存在额外资源块。新实现优先使用 CHARX，而不是继续扩展 PNG 资源块。

操作原则：

1. 用能保留未知 PNG chunk 的格式工具读取；
2. 保存像素数据、色彩配置、动画帧和所有非目标 chunk；
3. 只替换目标角色卡 chunk；
4. 不用截图、图像优化器或普通“另存为 PNG”重新编码角色头像；
5. 输出后重新扫描 chunk，解码 JSON 并与预期对象比较；
6. 若同时输出 V2 回填，明确记录 V3 → V2 的字段损失。

## JSON

- V2／V3 保留外层 `spec`、`spec_version` 和 `data` 层级；
- 不把 V2／V3 `data` 错写成 V1 平铺对象；
- 不按自己熟悉的字段白名单重建对象；对未知字段做深拷贝并原样写回；
- 保留字符串中的换行、宏、Unicode 和代码块，不进行无意义的 trim／格式替换；
- 序列化后再次解析，检查类型、必需字段和扩展对象。

## CHARX

V3 CHARX 是 ZIP：

- 根目录必须有 `card.json`；
- 资源按类型组织，路径区分大小写；
- 规范中的内嵌资源 URI 字面拼写是 `embeded://...`，不要“修正”成另一个字符串后破坏引用；
- 根目录还可能有应用专属 JSON；未知文件和未使用资源默认保留；
- ZIP 不应加密，成员路径优先 ASCII，避免跨平台兼容问题。

安全检查：

- 拒绝或隔离 `../`、绝对路径、设备名和路径穿越成员；
- 设定解压总大小、单文件大小和压缩比上限；
- 不执行内嵌代码；
- 检查远程资源 URI、数据 URI 和资源类型；
- 重新打包后按容器方式再次打开，不只看 ZIP 能否列目录。

## 内嵌 Lorebook 与应用扩展

V2／V3 `character_book` 和每个 entry 都可能包含未知 `extensions`。V3 Lorebook 还可能有 `use_regex`、可选字段与装饰器。迁移时：

- 保留条目 id、顺序、启用状态、关键词、secondary keys、position、priority、constant、case sensitivity、regex 标志和扩展；
- 不把不理解的字段全部设为默认值；
- 不把 SillyTavern 正则、酒馆助手脚本、MVU 配置或其他应用扩展误当标准字段删除；
- 若目标格式不支持某能力，把原值保存在可恢复位置并出具损失报告，不伪称无损；
- 单独导出 Lorebook 时，按目标版本的外层格式验证。

## 迁移策略

### V1 → V2／V3

- 映射六个核心字段；
- 新增字段使用规范合法的空值／默认值；
- 只在有来源时填写 creator、tags、版本和 notes；
- 历史未知字段先归档，再决定是否命名空间化放入 `extensions`；
- 不凭模型猜测补写作者元数据。

### V2 → V3

- 保留完整 V2 `data` 和各层 `extensions`；
- 设置 V3 spec 标记和必需的 `group_only_greetings`；
- 只在有资源时生成 `assets`；
- 保留来源和时间字段的语义，时间使用 UTC Unix 秒；
- 角色书按 V3 要求补字段时，不改变原有触发行为。

### V3 → V2／旧前端

这是可能有损的：`assets`、群聊专用开场、多语言 notes、source、nickname 和时间字段可能无法表示。只有用户明确要求兼容旧前端时执行：

- 始终保留原 V3 文件；
- 生成单独 V2 兼容副本；
- 在 creator notes 或交付报告中说明降级；
- 列出未映射字段和资源；
- 不让 V2 回填覆盖 V3 权威数据。

## Round-trip 验证

1. 保存输入哈希和完整结构快照；
2. 提取容器、JSON、资源清单和未知字段清单；
3. 对目标字段做最小修改；
4. 验证版本必需字段和字段类型；
5. 重新封装；
6. 用第二次解析重新读取输出；
7. 对 JSON 做结构差异：差异只能包含预期修改、允许的时间字段和明确迁移字段；
8. 对资源做路径、大小和哈希比较；
9. 对 PNG 检查图像仍可解码、角色 chunk 可解码；
10. 对 CHARX 检查 `card.json`、资源 URI 和无路径穿越；
11. 在目标 SillyTavern 的副本环境做导入预检或经授权的实际导入；
12. 再导出并比较，确认应用没有静默丢字段。

对于以 `index.yaml` 为源的项目，可用：

```text
node <skill>/scripts/check_character_roundtrip.mjs <项目目录> --artifact <最终卡包> --strict
node <skill>/scripts/check_character_roundtrip.mjs <项目目录> --readback <隔离回读目录> --strict
```

第一条只证明源项目与卡包一致；第二条才证明目标端重新读取的角色定义一致。使用 TavernSync 时再加 `--tavern-sync`，让空头像在 push 前失败。现有聊天是否显示新开场仍是独立的聊天历史验证，不由卡包哈希代替。

## 交付要求

报告输入格式、输出格式、规范版本、是否有损、保留了哪些未知字段／资源、实际做过哪些 round-trip 检查。没有经目标应用重导出的结果只能称为“格式级验证”，不能称为“完整导入导出无损”；只有 push stdout 而没有 API／pull 回读时，也不能称为“已导入”。
